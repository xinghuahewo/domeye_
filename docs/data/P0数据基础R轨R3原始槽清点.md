## 三、缺口形态：单一连续区间

`P0原始制品审计.json` 的 `missing_local_range`：

```text
start           : 2026-02-01T00:00:00+08:00
end_exclusive   : 2026-02-24T08:00:00+08:00
missing_update  : 6,720 槽
missing_rib     : 70 槽
```

23 天 8 小时 × 288 槽/天 = 6,720，与计数精确吻合。**缺口不是零散丢失，
而是窗口开头的一整段从未在本地留存**；本地 2 月数据仅覆盖 UTC 2026-02-24 至 02-28。

## 四、`parse_failed` 归因（34 UPDATE + 3 RIB）

基线报告已记录：UPDATE 目录发现 10,272 个槽，其中 **30 个压缩流 EOF/CRC 失败、
4 个为空文件**，故准入 10,238。

即 `parse_failed` 并非源不存在，而是**本地副本损坏或为空**。这类槽的源制品在
上游仍然存在，属可重取范畴，与 `source_unavailable` 的成因不同，
不应合并登记。

## 五、上游可得性核验（关键判定）

对缺口区间内的样本槽做 HTTP HEAD（**只核验，未下载**）：

| URL | 状态 | Content-Length |
|---|---|---|
| `https://data.ris.ripe.net/rrc25/2026.02/` | 200 | — |
| `https://data.ris.ripe.net/rrc25/2026.02/updates.20260210.0000.gz` | **200** | **6,984,275** |

`updates.20260210.0000` 落在缺口区间（2026-02-01 ~ 02-24）内。

**结论：6,790 个缺口槽在上游 RIPE RIS 仍然可得，不属永久不可恢复。**

这直接改变 R3 的性质：缺口成因是**本地未留存**，而非**源已灭失**。

## 七、范围决定（项目方，2026-07-26）

项目方决定：**接受 60.24% 覆盖率为最终，不执行补取。**

据此，6,790 个缺口槽的登记原因码为：

| 原因码 | 含义 | 槽数 |
|---|---|---:|
| `backfill_declined_scope_decision` | 上游可得，经项目方范围决定不补取 | 6,790 |
| `local_artifact_corrupt` | 本地副本压缩流 EOF/CRC 失败或为空（30 + 4 + 3） | 37 |

**该原因码刻意不使用 `unrecoverable`。** 上游可得性已核验（抽样 12/12 返回 200），
把可得的源登记为不可得会使验收记录失真；本项为范围决定，不是事实判断。
若将来重启补取，本文第五、六节的可得性与规模数据可直接复用。

## 九、对决策门的判定与后果

分阶段计划的门条件为："若槽覆盖远低于预期，全窗口 `raw_traceable` 可能不可达，
按 RFA-10 停在 `P0 历史数据兼容`。"

- 覆盖率 60.24%，**确属远低于预期**；
- 技术上 `raw_traceable` 仍可达（源可得），但**经范围决定不再追求**；
- 因此按 RFA-10：**只声明 `P0 历史数据兼容`，不得声明 `raw_traceable`**。

**后果：R 轨在 R3 终止。** R4（全窗口 RouteEvent 闭合）与 R5（全量语义复现与发布评审）
的出口均以全窗口原始追溯为前提，在 60.24% 覆盖率下不可能诚实达成，
故**不进入 R4/R5**——而不是在无法闭合的声明上继续推进。

若将来需要 R4/R5，须先撤销本范围决定并完成补取，或另立一个明确声明为
"限定于已准入 10,342 槽范围"的窄口径目标，该目标与本合同的 RFA-05/RFA-06 不同，
需要新的验收基准。

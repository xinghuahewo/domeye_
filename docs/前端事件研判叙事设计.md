# 前端事件研判叙事设计

## 1. 设计目标

当前事件页能展示事件记录、影响对象和证据缺口，但整体更像数据库详情页，还没有形成
完整的事件研判叙事。

前端不应只回答“数据库里记录了什么”，而应帮助用户依次理解：

> 发现了什么 → 为什么判定为异常 → 影响有多大 → 事件如何发展 →
> 哪些证据支持结论 → 还有什么无法判断 → 下一步做什么

## 2. 当前叙事缺少什么

现有内容已经覆盖：

- 现在是否异常；
- 异常从什么时候开始；
- 影响了多少国家、ASN、前缀和观测点；
- 影响是在扩大还是恢复；
- 哪些 ASN、前缀受影响最严重；
- 哪些原始 BGP 观测支持结论；
- 哪些信息目前无法判断。

但还缺少三个关键环节。

### 2.1 为什么它被判定为异常

页面需要先说明正常状态是什么，再解释发生了什么变化：

- 正常可见 ASN、前缀和 Prefix×VP 数量；
- ANNOUNCE、WITHDRAW 的正常区间；
- 当前值偏离正常值多少；
- 什么指标触发了检测规则；
- 连续多少个时间槽后正式确认异常。

没有正常基线，用户只能看到“数字发生变化”，无法判断变化是否显著。

### 2.2 控制面变化意味着什么

页面必须区分：

- BGP 控制面路由可见性；
- 数据面实际可达性；
- 用户流量和服务影响。

如果只有 BGP 数据，应明确写成：

> 已确认控制面路由可见性下降，实际用户流量和服务影响尚无数据支持。

不能把单个 collector 观察到的路由变化直接描述成“全国断网”。

### 2.3 用户看完以后做什么

事件页需要给出明确的下一步：

- 继续观察恢复；
- 查看全不可见 ASN；
- 查看重点前缀；
- 核对其他 collector；
- 查看原始 RouteEvent；
- 扩展更早的基线窗口；
- 扩展恢复观察窗；
- 补充数据面探测。

页面不只要给出结论，还要帮助用户继续调查。

## 3. 完整事件叙事

### 3.1 观测背景

首先回答“我们在观察什么”：

- 国家、ASN、前缀和地址族；
- collector 与 VP 范围；
- 固定 cohort；
- 数据截止时间；
- 当前数据是否完整。

然后说明正常情况下应该是什么样，包括正常可见率和正常波动范围。正常带不可用时，
直接显示原因，不使用异常窗口的第一个点冒充基线。

### 3.2 异常发现

说明具体发生了什么变化：

- WITHDRAW 是否突然增加；
- ANNOUNCE 是否异常波动；
- 可见 Prefix×VP 是否下降；
- 全不可见 ASN 是否增加；
- IPv4 与 IPv6 是否出现不同表现。

同时区分不同时间：

- 首次观察到变化；
- 达到异常门槛；
- 系统正式检出；
- 旧事实表记录时间；
- 影响峰值和可见率谷值。

页面不再只显示一个含义模糊的“事件时间”。

### 3.3 影响评估

除了受影响数量，还要展示：

- 受影响 ASN 数量、比例和固定分母；
- 全不可见与部分可见 ASN；
- Prefix×VP 可见率下降；
- IPv4、IPv6 分别受到的影响；
- 影响最严重的 ASN、前缀和 VP；
- 影响是否集中在少数网络或运营商。

所有比例都必须说明分母和观测范围。

### 3.4 事件演化

事件不应被简单切成三个固定空卡片，而应按照实际里程碑展示：

```text
首次变化 → onset → detected → peak → trough
→ 回升信号 → 部分恢复 → 完全恢复 → 观察结束
```

页面需要明确当前属于：

- 快速扩大；
- 持续恶化；
- 高位稳定；
- 出现回升；
- 部分恢复；
- 完全恢复；
- 观察结束但仍未恢复；
- 数据不足，无法判断。

如果存在多个阶段或波次，应展示 Incident、Episode 和 Wave 的关系，但不能因为时间
相邻就自动认定前兆导致主事件。

### 3.5 证据与可信度

证据应直接挂在结论下面。例如：

```text
22:00 受影响 ASN 达到 218 / 563
  ├─ 国家状态快照
  ├─ ASN 分类明细
  ├─ Prefix×VP 状态
  ├─ RouteEvent
  └─ 原始 MRT 坐标
```

用户可以从结论逐层下钻，而不是先阅读大量 evidence ID，再自行判断它们能证明什么。

页面还需要说明：

- 单 collector 还是多 collector；
- VP 覆盖是否完整；
- 原始报文是否可用；
- cohort 是否固定；
- 是否存在左删失或右删失；
- 哪些结论是事实、推导、推测或未知。

### 3.6 未知与下一步

“无法判断”应成为正式状态。页面需要同时告诉用户：

- 哪个问题无法判断；
- 为什么无法判断；
- 缺少什么数据；
- 如何补齐；
- 当前不能形成什么结论。

随后给出具体的调查入口或补数动作。

## 4. 建议的页面顺序

事件详情页从上到下建议调整为：

1. **事件结论**：当前状态、风险、onset、detected、数据截止时间；
2. **核心影响**：受影响 ASN、可见率、全不可见/部分可见、证据覆盖；
3. **为什么异常**：正常基线、检测信号、阈值和偏离幅度；
4. **趋势与里程碑**：变化、峰值、谷值和恢复状态；
5. **重点对象**：ASN、前缀、地址族和 VP 排行；
6. **结论与证据链**：每项结论对应的状态和原始观测；
7. **未知与下一步**：解释边界和建议动作；
8. **技术详情**：Incident ID、源表、schema、哈希和原始 JSON。

技术身份和证据登记簿仍然保留，但不再占据页面最重要的位置。

## 5. 最终需要回答的十个问题

完整的事件详情页应让用户快速回答：

1. 数据是否新鲜，观测范围是否可靠？
2. 正常状态是什么？
3. 发生了什么变化？
4. 为什么系统认为这是异常？
5. 异常什么时候开始，什么时候被发现？
6. 影响范围和严重程度有多大？
7. 影响集中在哪些 ASN、前缀、地址族和 VP？
8. 事件正在扩大、稳定还是恢复？
9. 哪些证据支持结论，哪些问题仍无法判断？
10. 用户下一步应该查看什么或采取什么行动？

## 6. 设计结论

事件页的核心叙事应从：

> 事件信息 → 缺失字段 → 证据登记簿

调整为：

> 观测范围 → 正常基线 → 异常信号 → 影响规模 → 演化与恢复 →
> 重点对象 → 证据链 → 可信度与边界 → 下一步行动

其中最需要补上的三个模块是：

1. 正常基线；
2. 为什么判定为异常；
3. 用户下一步行动。

这三部分补齐后，事件详情页才能从数据库详情页转变为真正的网络异常研判工作台。

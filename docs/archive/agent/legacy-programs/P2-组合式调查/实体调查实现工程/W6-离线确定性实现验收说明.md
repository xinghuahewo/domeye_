# W6 离线确定性实现验收说明

## 一、这次验收究竟通过什么

W6 验收的对象是 W5 已提交、已经过独立产品语义与 BGP 审查的同一实现候选。
最终状态 `implementation_accepted_for_release_preparation` 只表示：

1. W5 候选的运行时代码、Registry、Plan、ResultSet、EvidenceGraph、Answer/Turn、API、页面和本地 fixture 协议仍是同一组不可变字节；
2. 冻结 28 题的可执行性边界已经逐题、逐场景机器分类；
3. 本地确定性运行、取消、重跑、幂等、崩溃恢复、A/B 准入、无公开残留和边界攻击已经形成可重放证据；
4. 这份候选可以进入后续实际 provider 认证和独立发布准备。

它不表示 28 题已经得到正确答案，不表示实际 Sol/DS provider 已接入，不表示
provider 模型对齐、provider 性能或费用通过，也不授权运行时晋级、生产部署或流量切换。

## 二、为什么 168 个 case 都能“通过”，但问题答案仍未通过

冻结 Oracle 为每题规定六个必测场景：正常、空、缺失、错误身份、边界和大结果，
共 `28 × 6 = 168` 个 case。W6 的 `case_passed=true` 表示“当前实际分类与冻结
期望一致”，不是“该问题答案正确”。

当前候选的诚实统计为：

- 27 题、162 个 case：`correctly_blocked`；
- Q24 的 6 个 case：`correctly_deferred`；
- `executed_supported`：0；
- `correctly_bounded`：0；
- 完整问题回答认证：`false`。

阻断主要来自旧 P1 单元没有进入 W5 统一 Dispatcher、ResultSet 到 Operator 的受信
人口投影/绑定适配器缺失、动态成员 fan-out 没有准入、正式 planning allowlist 不完整，
以及固定 fixture 的 ASN/路径样本不足。Q24 使用的 TOOL-13、OP-34 属于 P2.1，必须
零执行并显式延期。Q20、Q23、Q26 仍是主问题阻断，只有其中动态 fan-out 子目标延期，
不能把子目标延期改写成整题已经支持或整题已经延期。

`expected` 只来自冻结分类合同；`actual` 由另一条机器路径从 W5 execution admission、
正式 planning allowlist、source-store 人口、版本化 Host adapter 合同探针和 P2.1
Dispatcher 拒绝结果推导。分类发生在执行前，因此阻断 case 明确记录
`execution_started=false`、`observed_zero_fact_commit=false`，不把“没有启动”伪写成
“运行后观察到零提交”。Q24 则实际调用 Dispatcher 拒绝入口，逐项取得
`p2_1_unit_forbidden`，并证明 handler 调用数为零。

## 三、同候选证据

实现候选身份只由 W5 提交、W5 evidence/stage receipt、执行准入、Registry snapshot、
source-store、Oracle 及 W5 50 项实现制品构成。W6 Hook、认证脚本、case 输出、review
和 acceptance manifest 都不进入候选身份，避免认证结果反向改变被认证对象。

W6 会复用并重验 W5 的实际 14 事件准入链，确认 Plan A→Plan B→running→首次业务
dispatch→ResultSet A/B/publish→EvidenceGraph A/B/receipts/publish→最终 CAS 的顺序，
并确认动态 fan-out、任意 callback、P2.1 单元和外部 provider 调用均为零。

## 四、性能、恢复和费用边界

本轮只接受离线确定性运行时的测量与恢复：

- W5 runtime/API、W5 Sidecar 和 W6 recovery runner 都绑定真实子进程回执；
- 本地 runner 耗时必须落在版本化阈值内；
- CAS journal 崩溃恢复、pointer/idempotency 次序、取消胜出、局部重跑、幂等冲突、
  ResultSet/Graph A/B 失败无未准入公开残留必须通过；
- 外部 provider 调用数固定为 0；fixture 费用只能写成 synthetic fixture receipt；
- provider billed amount 和 provider price attestation 必须为 `null`。

因此可写“离线确定性运行时性能已验收、恢复已验收”，不能写“实际 provider 性能或
费用已经验收”。

## 五、独立审查与退出条件

产品语义 reviewer 必须确认 28 题/168 case 人口、阻断/延期含义和用户边界没有偷换；
BGP reviewer 必须确认范围仍是单一 RRC25 publication、控制面观测不被提升为 customer
cone、商业关系、全国/用户影响、原因、责任、恢复或 RCA。两位 reviewer 只读、身份
不同、互不引用，也不得引用最终 acceptance manifest 形成摘要环。

独立审查合同允许 reviewer 返回 `revision_required` 并列出阻断或越级发现；只有
`review_disposition=accepted_for_pre_provider_release_preparation_with_explicit_question_blocks`
且两类问题列表均为空时才可进入最终清单。评审输入同时绑定分类合同、case matrix、
certifier manifest、case index、运行、性能和攻击制品，任一受审字节变化都会使旧审查失效。

攻击证据固定为 24 项。每项必须包含实际变异输入摘要、真实 verifier 入口和拒绝码；
禁止用手写 `rejected=true` 代替运行。覆盖 JSON/JSONL、Oracle 拼接、候选/Registry/
publication 换绑、阻断冒充执行、通用边界冒充题目特定回答、缺失 A/B 准入、隐藏 fan-out、
路径逃逸以及 review/acceptance 摘要环。

只有 168 个分类、实际 W5 proof、恢复/攻击、离线性能、三份 W6 runner 和两份独立审查
全部闭合时，W6 才能签发 `implementation_accepted_for_release_preparation`。此状态仍然
禁止合入生产主干、部署、流量切换和线上模型晋级。

# RRC25 伊朗事件 18:05–23:00 状态重放与事件模型改造需求

## 1. 任务结论

本任务只完成两个目标：

1. 使用最近的 RRC25 bview，对北京时间 2026-02-28 18:05–23:00 进行一次有界
   路由状态重放；
2. 根据重放得到的逐槽状态，改造旧 `country_outage` 事件模型，解决事件时间、
   峰值集合、分子分母和恢复状态互相覆盖的问题。

本任务明确允许修改不合理的 `backend/core/BGPOutage.py` 和
`backend/database/country_outage.py`。该授权只覆盖国家中断事件模型及其必要的
兼容接口，不扩大到其他五类异常检测逻辑。

### 1.1 最终目标

最终目标不是“把文件跑完”或“再生成一份研究报告”，而是：

> 用 18:05–23:00 的真实逐槽路由状态，建立一条结构化、时间语义一致的伊朗国家
> 中断事件；并让改造后的旧系统能够直接生成和读取这种事件，不再依赖不断覆盖的
> 峰值摘要。

任务最终完成必须同时满足：

1. 成功生成 18:05 起点状态和 59 个槽末状态；
2. 能列出每槽可见、受损、恢复和未恢复的伊朗 ASN；
3. 生成包含九个明确事件字段的 Incident/Episode v2；
4. `BGPOutage.py` 不再混用检测、峰值和恢复时间；
5. `country_outage.py` 能持久化新模型，并为旧接口提供兼容投影。

只完成重放、只改数据表或只写报告，都不算达到最终目标。

### 1.2 开发与执行原则

- 现有逻辑能复用就复用；遇到缺失、不合理或难以复用的逻辑，可以直接编写新的
  实现，不要求绕行旧代码；
- 新逻辑优先写成边界清晰的模块，再接入 `BGPOutage.py`，避免继续扩大单个旧函数；
- 只做保障结果正确所必需的检查，不开展繁琐的审计、审批、双人复核或逐条证据验收；
- 不引入额外的事件级聚合证据包，也不要求每条状态都闭合到 raw record ordinal；
- 不重复执行相同的真实重放来证明可复现；真实数据正式运行一次即可；
- 不得擅自设置单文件处理时间上限、总运行时间上限、软超时或因运行较慢主动终止；
- 只要没有数据错误、解析错误、资源耗尽或用户中止，处理应持续运行直到完成；
- 可以记录运行耗时用于观察，但耗时不得作为成功或失败的验收门槛。

## 2. 固定研究边界

- 59 个槽末状态；

如果后续要求处理 `23:00–23:05` 这一槽，应显式把窗口终点改为 23:05；本任务不

## 3. 目标一：逐槽路由状态重放

### 3.1 重放状态键

复用现有确定性状态机，状态键固定为：

```text
collector + VP + AFI/SAFI + canonical prefix
```

处理语义：

- RIB/ANNOUNCE：替换同一状态键的当前路由；
- WITHDRAW：只删除同一 VP、同一 AFI、同一 Prefix 的状态；
- 事件顺序：`event_time → artifact_slot → record_ordinal → element_ordinal`；
- 五分钟槽：`[start, end)`；
- 边界时刻事件进入下一槽；
- 输入出现缺口后，连续性必须变为 `unknown_after_gap`，禁止继续输出伪造数值。

优先复用：

```text
backend/data_pipeline/research/rrc25_country_outage/state_replay.py
backend/data_pipeline/research/rrc25_country_outage/sample_builder.py
backend/data_pipeline/research/rrc25_country_outage/episodes.py
```

### 3.2 伊朗路由人口

使用冻结的 AS→国家映射，先从 bview 确定窗口起点实际可见的 IR origin ASN、
Prefix 和 VP。

必须分别保留：

- IPv4 origin ASN 集合；
- IPv6 origin ASN 集合；
- 双栈并集；
- 每个 ASN 的基线 Prefix；
- 每个 Prefix 的基线 VP；
- AS_SET、无 origin、映射缺失和映射冲突。

未知或冲突不能默认归入 IR，也不能默认排除后再伪装为完整人口；必须进入质量报告。

为正确处理无 AS_PATH 的 WITHDRAW，前缀预过滤集合至少包含：

1. bview 中 origin 映射为 IR 的 Prefix；
2. 84 个 UPDATE 中 ANNOUNCE origin 映射为 IR 的新增 Prefix；
3. 上述 Prefix 的全部相关 WITHDRAW。

### 3.3 每个状态观察点必须输出

国家级：

- `snapshot_id`；
- `observed_at`；
- `continuity_state`；
- 基线 cohort ID 与映射版本；
- IPv4/IPv6/双栈可见 origin ASN 集合；
- IPv4/IPv6 可见 Prefix 集合或内容寻址引用；
- 基线 ASN 总数、当前可见数、受影响数和比例；
- 基线 Prefix×VP 总数、当前可见数、损失数和比例；
- 本槽 ANNOUNCE/WITHDRAW 只作为辅助消息指标。

ASN 级：

- ASN；
- 地址族；
- 基线 Prefix 数；
- 当前可见 Prefix 数；
- 基线 Prefix×VP 数；
- 当前可见 Prefix×VP 数；
- 首次受损时刻；
- 首次完全不可见时刻；
- 首次恢复时刻；
- 截止观察结束是否恢复；
- 支持状态变化的来源文件、时间槽和动作摘要。

Prefix×VP 级：

- Prefix、AFI、VP；
- 当前是否可见；
- 当前 origin；
- 最近动作及时间；
- 最近来源 UPDATE 文件或 bview 槽；
- 为调试自然产生的 RouteEvent 信息可以保留，但 raw record ordinal、element
  ordinal 和逐条内容哈希不是本任务验收条件。

### 3.4 ASN 可见性分类

必须先按地址族分类，再生成双栈联合分类，不能直接把 IPv4 与 IPv6 相加。

单地址族：

```text
fully_visible:
当前仍保留全部基线 Prefix×VP 状态

partially_visible:
当前保留数大于 0 且小于基线数

fully_invisible:
当前保留数为 0

unknown:
输入不连续、基线缺失或映射冲突
```

双栈联合：

- `fully_invisible`：该 ASN 在所有基线地址族均为 fully_invisible；
- `partially_visible`：至少一个地址族仍可见，但未保持全部基线状态；
- `fully_visible`：所有基线地址族均保持全部基线状态；
- `ipv4_invisible_ipv6_visible`：作为独立标签保留；
- `unknown`：任一关键地址族状态未知且无法安全归类。

必须同时输出：

- 基线人口；
- 每个分类的成员集合；
- 分子、分母；
- 地址族；
- snapshot ID；
- 算法版本。

不得为了匹配报告的 `199/595` 或 `73/126` 调整口径。

### 3.5 必须回答的问题

重放结束后必须能够回答：

1. 18:05 窗口起点实际可见的 IR origin ASN 有多少；
2. 每槽 IPv4、IPv6 和双栈可见 ASN 集合如何变化；
3. 哪些 ASN 最先受损；
4. 哪些 ASN 在最大受损快照完全不可见或部分可见；
5. 哪些 ASN 在窗口内恢复；
6. 哪些 ASN 到 23:00 仍未恢复；
7. 是否存在恢复后再次下降；
8. 18:05–23:00 内形成零个、一个还是多个 Episode/Wave；
9. 状态结果与数据库聚合曲线在哪些时间点一致或不一致；
10. `199/595`、`73/126`、`176/556` 在统一口径下分别如何评价。

## 4. 目标二：事件事实模型改造

### 4.1 模型原则

必须把以下对象分开：

```text
Incident：检测系统记录的事件容器
Episode：连续的路由状态异常阶段
Observation：不可变的五分钟状态快照
Milestone：由具体 Observation 支撑的阶段时间
SourceContext：本次 bview、UPDATE 范围和必要来源信息
```

一个旧 Incident 可以关联零个、一个或多个 Episode。时间先后不等于因果关系。

### 4.2 新事件字段

API 和持久化模型必须显式提供：

| 字段 | 语义 |
| --- | --- |
| `detected_at` | 检测系统首次创建/告警该 Incident 的时间 |
| `onset_at` | 状态数据确认 Episode 开始的第一个异常槽 |
| `peak_at` | 受影响 ASN 比例达到最大值的快照时间；并列取最早 |
| `trough_at` | 基线 Prefix×VP 可见比例达到最低值的快照时间；并列取最早 |
| `partial_recovery_at` | 连续 6 槽达到基线 99% 的首槽时间 |
| `full_recovery_at` | 连续 6 槽回到正常波动带的首槽时间 |
| `observation_end_at` | 本次证据实际观察截止时间 |
| `duration_state` | `exact/lower_bound/interval/unknown` |
| `recovery_state` | `ongoing/recovering/partially_recovered/fully_recovered/unknown` |

每个阶段字段还必须绑定：

- `snapshot_id`；
- 算法版本；
- 使用的指标；
- 指标值；
- 时间精度或未知原因。

### 4.3 数据表职责

建议最小拆分为三层。

#### Incident/Episode 主表

保存：

- 稳定 incident/episode ID；
- source、country、collector；
- 上述阶段时间；
- duration/recovery 状态；
- cohort ID；
- peak/trough snapshot ID；
- 当前算法版本；
- legacy ref；
- 创建时间和最后派生时间。

主表是当前可查询投影，不保存大规模 Prefix×VP 明细。

#### Observation 表

按五分钟追加写入，不允许覆盖：

- snapshot ID；
- observed_at；
- 连续性；
- 同快照 ASN/Prefix/Prefix×VP 统计；
- IPv4/IPv6 分类集合或内容寻址引用；
- 状态结果文件路径。

#### 重放结果文件

大规模明细使用 create-only JSONL gzip：

- route state；
- ASN state；
- 国家逐槽状态；
- Incident/Episode/Wave；
- 简要输入说明；
- 简要质量结果。

数据库只保存结果路径、snapshot ID 和必要统计，不把完整 Prefix×VP 状态塞进事件
摘要。逐条 raw ref、完整内容寻址 inventory 和独立审计包不属于本任务强制产物。

### 4.4 旧字段兼容

旧字段保留一轮兼容，但不再作为新模型的事实来源：

| 旧字段 | 新行为 |
| --- | --- |
| `s_time` | 兼容投影为 `detected_at`，不得冒充 `onset_at` |
| `e_time` | 只有 `fully_recovered` 才可投影 `full_recovery_at`；旧值单独标记 legacy |
| `duration` | 根据 `duration_state` 派生，不能用观察截止伪造精确时长 |
| `event_info` | 由结构化事实生成，不再从字符串中反推时间或数值 |
| `outage_ases` | 只允许投影 peak snapshot 的成员集合，并绑定 snapshot ID |
| `total_as_num` | 必须来自同一 cohort/snapshot |
| `max_outage_as_num` | 必须与 peak snapshot 绑定 |
| `max_outage_as_ratio` | 必须由同一 snapshot 的分子分母计算 |

旧历史记录迁移时：

- 可以把原 `s_time` 标记为 legacy detected_at；
- 不得用 `event_info` 时间填充 `onset_at/peak_at/trough_at`；
- 不得用旧 `e_time` 直接确认 full recovery；
- 无法复算的字段保持 NULL/unknown；
- 保留原值和 migration note，禁止伪造新证据。

### 4.5 Core 改造要求

`BGPOutage.__check_country_outage` 应从“直接修改峰值摘要”改为：

1. 每个五分钟周期生成结构化 `CountryOutageObservation`；
2. 纯状态转换器消费 Observation；
3. 独立计算 Incident/Episode/Milestone；
4. Repository 负责事务写入；
5. `event_info` 在输出层生成；
6. 邮件、总事件表和详情接口从结构化事实读取。

必须消除以下旧行为：

- `max_outage_as_num`、`max_outage_as_ratio`、`total_as_num` 分别在不同时间更新；
- `outage_ases` 与 max count/ratio 没有 snapshot 绑定；
- 峰值刷新时覆盖 `event_info` 中的时间；
- 单槽超过 98% 就直接结束事件；
- `s_time/e_time` 同时承担检测、状态和恢复语义。

数据库写入必须参数化、事务化；测试中失败不得留下半写入 Incident 或 Observation。

## 5. Episode 与恢复规则

本任务先使用冻结规则，不在执行时调参：

- 检测触发：受影响 ASN 比例首次超过 3%；
- onset：连续 2 槽超过 3% 后，回指确认序列的首槽；
- peak：最大受影响 ASN 比例快照；
- trough：最小 Prefix×VP 可见比例快照；
- 部分恢复：可见 origin ASN 比例与 Prefix×VP 可见比例均连续 6 槽达到基线
  99%；
- 完全恢复：上述两个状态指标均连续 6 槽回到冻结的基线正常波动带；
- 观察截止仍未完全恢复：`duration_state=lower_bound`；
- `full_recovery_at=null`；
- 短暂单槽跨线不能结束 Episode；
- 完全恢复后再次异常才允许产生新 Episode；
- 未完全恢复前的二次下降属于同一 Episode 的新 Wave。

基线正常波动带优先由 bview 后、18:05 前的 catch-up 状态序列生成，并记录实际
使用的槽。如果该序列已异常或不稳定，完全恢复判定必须为 unknown，不得临时放宽
阈值。

如果 18:05 起点已经处于异常状态，且 catch-up 状态不能定位由正常转异常的边界，
`onset_at` 必须标记为左删失/区间或 unknown，不能为了匹配数据库代理而强制写成
18:05。

由于本窗口只到 23:00，不得使用窗口外数据库数据填充本次 replay 的
`partial_recovery_at/full_recovery_at`。如果窗口内没有恢复，必须输出 NULL 和
lower bound。

## 7. 验收标准

### 7.1 重放验收

- 精确使用 1 个 bview 和 84 个 UPDATE；
- 检查输入文件存在、时间连续、角色正确且压缩可读；
- 输出 1 个起点状态和 59 个槽末状态；
- 每槽都有 IPv4、IPv6、双栈 ASN 集合；
- 每个数值都有同 snapshot 分子、分母和 cohort ID；
- ASN 状态能够定位到 Prefix×VP；
- 能列出首先受损、peak 不可见、恢复和未恢复 ASN；
- 能判断 Episode/Wave 数量；
- 输入缺口时失败关闭，不用 0 填充；
- 正式真实数据只运行一次，不要求为了验收再做第二次完整重放；
- 不设置单文件或总执行时间上限。

### 7.2 模型验收

- 九个新字段均有明确结构化语义；
- detected/onset/peak/trough/recovery 时间不再混用；
- `outage_ases`、count、ratio、total 绑定同一 snapshot；
- `event_info` 不再是事实来源；
- 短暂恢复不会关闭事件；
- 未完全恢复时 duration 为 lower bound；
- 一个 Incident 能关联多个 Episode；
- 旧接口可兼容读取，但明确标记 legacy 语义；
- 历史迁移不伪造未知字段；
- 数据库事务失败不会留下半成品；
- 本次伊朗结果能够通过新模型读取和解释。

### 7.3 必测场景

- count 峰值与 ratio 峰值发生在不同槽；
- total population 在事件中变化；
- `outage_ases` 与 peak snapshot 不一致时拒绝写入；
- 单槽超过 98% 后再次下降；
- 连续 6 槽部分恢复；
- 连续 6 槽完全恢复；

## 二、当前生产者身份现状（RFA-01 入口证据）

数据库转储制品**不绑定任何生产者代码身份**：

- `database-inventory.json` 顶层键：`tables`、`data_start`、`snapshot_time`、`schema_version`、`integrity`；
- 每表键：`name`、`max_time`、`min_time`、`row_count`、`schema_hash`——只有形状、体量与时间；
- `manifest.json` 记录 release、创建时间与制品哈希，不记录产出代码；
- 全库 109 张表的 `database-schema.sql` 中，`version` 仅命中 2 处，均为 `pg_dump` 自身版本；
- 事实表列中没有 `ingest_time`、`parse_time`、`detect_time`、算法版本或实例标识；
  `source varchar(2)` 是数据来源代码（`r`/`c`），**不是**生产者代码身份。

结论：**生产者身份在数据层完全缺失**，与 R0 入口描述一致，且已取得证据。

## 三、可恢复性结论：必须按检测侧与特征侧分开

R0 的结论必须分成两个维度，二者结论相反：

| 身份维度 | 覆盖范围 | 结论 |
|---|---|---|
| 实例身份（PID）与表归属 | 全窗口 | **可恢复**（运行日志） |
| 检测侧代码内容身份 | 全窗口 | **不可恢复**（生产进程均早于可信代码快照） |
| 特征侧代码内容身份 | 2026-02-24 ~ 2026-03-12 09:47（北京） | **不可恢复** |
| 特征侧代码内容身份 | 2026-03-12 10:30（北京）起 | **可按进程启动 HEAD 恢复** |

**关键约束：当前仓库各引用中最早可见快照仍晚于 PID 32082 的
`2026-03-07 02:45:11 UTC` 启动时刻；主线用于绑定的首个可信提交为
`6f01237`（2026-03-07 08:52:30 UTC）。** 因此不能证明任何 Git 快照就是
该进程导入时的源码。R0 使用原因码“进程启动时不存在可信快照”，不再断言
“仓库当时不存在”。

## 四、关键发现：代码状态由进程启动决定

Git 提交发生不等于运行中进程加载了新代码。生产者身份必须按
**(表, 生产进程观察区间)** 绑定；只有进程重新启动后，启动时 HEAD 才能作为该段代码身份。

`c0f3be3`（2026-03-25 07:27:17 UTC）引入前缀规范化与跳过判定：

```diff
-  version = ipaddress.ip_network(prefix, strict=False).version
+  normalized_prefix, version, prefixlen = normalize_bgp_prefix(prefix)
+  skip_reason = get_feature_prefix_skip_reason(version, prefixlen)
+  if skip_reason is not None:  # v4 </8, v6 </16 被跳过
```

但固定日志前缀中最后一个实际产生 insert 的主特征进程 PID 67265 于
`2026-03-25 06:54:53 UTC` 启动，早于该提交 32 分 24 秒；之后至窗口结束
没有加载 `c0f3be3` 的生产进程。因此该提交没有形成二三月数据的方法学断点，
A1 对本窗口不成立。该结论仅说明代码路径未被加载，不等于数据正确。

另：`FEATURE_EXCLUDED_PREFIXES` 注释日期为 2026-04-06，晚于窗口，**不参与二三月论证**
（与 S6 排除结论一致）。

## 六、关键发现二：进程生命周期决定代码状态，而非提交时间

Python 在导入时绑定模块，**运行中的进程不会加载其启动之后的提交**。因此代码状态由
进程启动时刻决定。

检测侧的实际情况：

> **时区更正（2026-07-26）**：日志时间戳为北京时间（UTC+8），Git 提交时间为 UTC。
> 依据：该日志文件 mtime `2026-04-28 05:37:24 +0000` 与末行 `2026-04-28 13:37:24` 相差恰 8 小时。
> 本节初稿未做换算，曾误判进程启动时的 HEAD，现已按 UTC 重算。

- `bgp-2026-03-07-32082.log`：PID 32082，**北京时间 2026-03-07 10:45:11 启动
  （= UTC 02:45:11），持续运行至北京时间 2026-04-28 13:37:24**（52 天）；
- 该进程写入 `prefix_outage_202603` 与 `prefix_outage_202604`；
- 2026-03-07 至 2026-04-28 之间**没有其他检测日志**，即窗口后段由该单一进程独占产出；
- 其启动时刻 `2026-03-07 02:45:11 UTC` **早于仓库首次提交 `6f01237`
  （2026-03-07 08:52:30 UTC）6 小时 7 分**。

由此得到一条重要**代码事实**：该进程运行的源码早于全部 Git 历史，因此窗口内
**检测侧数据的代码内容身份 100% 不可由 Git 恢复**；`a6a138e`(03-13)、`1a4a603`(03-15)、
`234976b`(03-18)、`c0f3be3`(03-25) 四次提交虽落入窗口，但均**未被该运行进程加载**。

完整绑定结果见 [R0 生产者身份绑定表](./P0数据基础R轨R0生产者身份绑定表.md)。

特征侧记录形态不同：`logs/feature_log` 为单一追加日志（6.1 GB），跨度
2026-02-24 12:10:31 至今，行号指纹随版本变化（如 `BGPFeature.py[line:640]` →
`[line:1046]`），可据此切分版本区间。

# 主干开发与发布归一治理规范

## 一、目的与边界

本文把 Domeye Core 的任务 Worktree、Git 分支、发布 tag、不可变制品和生产运行时
收敛为一条可审计链路，防止以下状态被混为一谈：

- 临时任务 Worktree 被当作长期生产主干；
- 源码仓库检出、发布 tag、源码归档和实际进程身份不一致；
- 候选、金丝雀和生产分别构建，导致验收对象与上线对象不同；
- `merged`、`built`、`certified`、`deployed` 和 `verified` 被越级宣告；
- 仅凭 Screen、软链接、HTTP 200、页面可见或目录名证明生产完成。

本文只治理版本和发布身份，不改变 RRC25 数据语义、业务功能、数据库内容、模型
合同、模型认证规则或生产安全边界。治理发布不得调用 DeepSeek；需要模型认证的业务
发布必须另行取得明确授权和费用上限。

## 二、唯一长期身份

永久身份固定为：

| 对象 | 唯一身份 | 职责 |
| --- | --- | --- |
| 生产主干 | `main` | 只接收具有评审和 CI 证明、可进入发布候选的提交 |
| 本地主干检出 | `/Users/botongwu/Documents/domeye/core-work` | 指向生产远端的永久独立 clone，固定检出 `main` |
| 任务分支 | `codex/<task>` | 单一任务的短生命周期分支 |
| 任务 Worktree | 独立任务目录 | 单一任务的隔离检出，不得直接作为生产身份 |
| 发布身份 | 带注释的不可变 tag | 绑定正式发布提交和发布说明 |
| 生产制品 | runtime `releases/<release-id>` | 从同一发布提交一次构建并按摘要冻结的组件制品 |
| 生产指针 | `current`、状态文件与运行管理状态 | 只指向已激活的不可变制品 |

`core-work` 是独立 clone，不依赖旧 `core-prod08-work` 的 Worktree 元数据。新的短期
任务 Worktree 从 `core-work` 创建。Worktree 只是检出载体，不是版本、候选或发布
身份；任务结束时整合的是已评审提交，禁止复制兄弟 Worktree 的未提交文件。

生产服务器 `/home/bgpdata/Domeye-Core` 的当前检出可用于只读诊断和接收 Git 引用，
但其 `HEAD`、分支名和脏净状态不代表运行制品。生产身份必须从 `main` 引用、
annotated tag、源码归档、组件清单、活动指针和实际进程共同取得。

## 三、标准开发与整合流程

```text
明确 main 基线
  ↓
短生命周期任务分支与独立 Worktree
  ↓
TASK.json + codex-preflight
  ↓
最小修改 + 影响面测试 + codex-postflight
  ↓
评审与 CI 证据
  ↓
服务器端保护 Hook 允许快进 main
  ↓
正式 annotated tag
  ↓
从最终提交一次构建并冻结统一制品
  ↓
候选验证 → 金丝雀 → 同制品生产晋级
  ↓
生产验证与发布归一检查
  ↓
任务 Worktree 受控退役
```

普通任务不得直接在 `core-work` 修改。跨分支整合、发布归一和紧急修复必须使用
独立任务合同，明确源提交、目标提交、允许路径、禁止路径、发布影响和回滚边界。
未完成能力使用明确开关或未接线入口隔离，不通过长期发布分支维持第二套事实主干。

## 四、变更状态必须分开

| 状态 | 机械证据 | 不代表 |
| --- | --- | --- |
| `implemented` | 任务差异和定向测试通过 | 已提交或已评审 |
| `committed` | 任务分支存在明确提交 | 已推送或已评审 |
| `reviewed` | 人工评审结论和 CI 证据存在 | 已进入生产主干 |
| `merged` | 提交是 `main` 的祖先 | 已构建或已部署 |
| `built` | 不可变统一制品及摘要存在 | 已认证或已激活 |
| `certified` | 专项认证证据绑定同一制品 | 已部署 |
| `staged` | 候选或金丝雀运行同一制品 | 生产已切换 |
| `deployed` | 生产指针和实际进程使用该制品 | 生产效果已通过 |
| `verified` | 生产身份、接口、边界和效果门禁均通过 | 后续永不回滚 |
| `rolled_back` | 生产身份恢复并通过回滚验证 | 新制品已删除 |

Hook、测试、tag、Screen 会话、端口监听、HTTP 200 和可见页面只能证明各自覆盖的
事实，不能单独证明 `deployed` 或 `verified`。

## 五、服务器端主干与 tag 保护

服务器端 Hook 的版本化来源为
[`deploy/governance/pre-receive`](../deploy/governance/pre-receive)，安装位置为
`/home/bgpdata/Domeye-Core/.git/hooks/pre-receive`。它失败关闭并执行：

1. `main` 禁止删除、强推和非快进更新；
2. 每个新的 `main` 目标提交必须有 root 持有、不可被组或其他用户写入的
   评审与 CI JSON；
3. 已存在 tag 禁止修改或删除；
4. 时间戳形式的正式发布 tag 必须是 annotated tag，且其提交已经进入本次或当前
   `main`；
5. 普通任务分支仍可推送，但推送不等于评审、合并或发布。

审批文件默认位于
`/home/bgpdata/Domeye-Core-governance/approvals/<commit>.json`。仓库本地配置
`domeye.governanceApprovalRoot` 只用于显式指定同等受控的绝对目录；修改该配置本身
属于服务器治理变更，必须留下审计记录。审批 JSON 至少包含：

```json
{
  "schema_version": "domeye_main_approval_v1",
  "commit": "40位提交",
  "review": {"status": "approved", "evidence": "证据引用"},
  "ci": {"status": "passed", "evidence": "证据引用"},
  "approved_at": "UTC时间"
}
```

Hook 只判断是否允许更新 Git 引用，不代替构建、部署或生产验证。

## 六、一次构建、逐级晋级

同一正式发布只允许从一个冻结提交生成一次统一候选。候选至少绑定：

- Git commit 与 annotated tag；
- 源码归档路径、SHA-256 和文件清单摘要；
- `backend/core.sha256` 校验结果；
- Backend、Sidecar 和 Frontend 的 release ID、路径及目录摘要；
- 模型注册表、认证证据或“本次不调用模型”的明确边界；
- Nginx 配置摘要；
- 数据档和数据库状态摘要；
- 构建工具链版本和生成时间。

候选、金丝雀和生产必须晋级同一份不可变制品。正式候选形成后重新复制源码、安装
未锁定依赖或重新构建任一组件，都会形成新候选，旧候选的认证和验收不得沿用。
运行时配置可以按批准边界注入，但必须记录摘要，不能改写制品内容。

## 七、发布归一条件

生产验证结束时必须同时成立：

```text
core-work HEAD
= origin/main
= release tag 解引用后的 commit
= 源码归档绑定的 Git commit
= Backend、Sidecar、Frontend 清单绑定的 Git commit
```

并分别验证：

```text
Backend 实际进程目录与 release ID = Backend current
Sidecar active state 与实际进程 = Sidecar current
Frontend 线上文件逐字节 = Frontend 候选 dist
Nginx 配置摘要 = 本次冻结摘要
数据库状态摘要 = 本次批准摘要，且 changed = false（治理专用发布）
```

版本化只读检查入口为
[`deploy/governance/check-release-normalization.sh`](../deploy/governance/check-release-normalization.sh)。
它读取仓库外统一发布证据并核对 Git、归档、三类制品、实际进程、Nginx、数据库和
生产验证状态。任一项不一致，发布状态最多为 `deployed_identity_drift`，不得宣布
`verified`。禁止通过改写证据、移动软链接或只重启进程掩盖漂移。

## 八、Worktree 生命周期

任务 Worktree 状态固定为：

- `active`：正在实施单一任务；
- `integrated`：提交已进入 `main`，等待退役；
- `excluded`：经评审确认不属于当前主干；
- `abandoned`：任务终止，提交不进入主干；
- `retired`：本地检出已移除，历史由 Git 和制品保留。

只有同时满足以下条件才能退役：

1. 无暂存、未暂存和未跟踪业务文件；
2. 任务提交已经推送；
3. 提交已进入 `main`，或有明确的 `excluded` / `abandoned` 决议；
4. 验收证据已进入版本库或仓库外不可变证据目录；
5. 不被活动发布、回滚、锁、挂载、进程或其他 Worktree 引用；
6. 先生成 dry-run 清单，再逐个确认精确路径。

退役只使用 `git worktree remove <精确路径>` 移除检出；分支、提交、tag、审批和发布
证据按保留策略处理。禁止用递归删除代替受控退役，也禁止自动合并所有旧 Worktree。

## 九、历史 G2 记录与本次 `main` 迁移状态

本规范最初在 `9bbcb1b` 建立；G2 曾从当时已验证的旧生产引用 `b6440cc` 重新评审并移植，
不直接 cherry-pick 旧分支。发布前后状态必须以实时证据为准，不以本节目录名代替
重新清点。

以下只记录当时的 G2 历史事实，不把旧状态改写成当前 `main` 已完成：

| 项目 | 当时的 G2 边界 |
| --- | --- |
| 永久生产引用 | 当时使用旧生产引用，G2 只允许快进 |
| 永久本地 clone | `core-work` 当时跟踪旧生产引用，发布验证后再快进到 G2 |
| 旧临时整合 Worktree | 只作为旧 Git 元数据锚点保留，不再承担生产身份 |
| 已整合阶段 Worktree | 满足条件者已经退役；新发现或新建任务按第八节重新分类 |
| 未整合工作 | `project-docs-work`、`rrc25-go-work` 明确 `excluded`，不自动合并 |
| 旧治理 Worktree | 仅作为 `9bbcb1b` 只读来源，G2 verified 后退役 |
| 分支保护与归一检查 | 服务器已启用；G2 将其版本化、测试并以同制品发布证明源码一致 |

本次 `main` 迁移的状态必须单独表达：

| 项目 | 当前状态 |
| --- | --- |
| 仓库规则、Hook 源码、归一检查、运行验证与夹具 | 已在任务分支统一指向 `main`；本地正反夹具通过 |
| GitHub 默认分支 | 已只读确认为 `main` |
| 生产服务器 Git `refs/heads/main` | 未现场读回，不得推定存在或指向当前 Candidate |
| `core-work` checkout 与 upstream | 未现场读回，不得推定已跟踪 `origin/main` |
| 服务器已安装 Hook 与审批 schema | 本任务未安装、未读回摘要；仓库源码变化不会自动更新服务器 |
| 当前 release 归一检查 | 未以本次 Candidate 在生产执行 |

因此当前只能声明“仓库定义已迁移”。生产 cutover 必须由单独的高风险任务执行：先
只读冻结旧 ref、`core-work` upstream、Hook/归一脚本和审批目录摘要；再确认目标
`main` 完整 SHA 与审批文件，安装同一 Candidate 的治理脚本；最后读回 ref、upstream、
安装回执、脚本 SHA-256、Hook 夹具和当前 release 归一结果。任一步失败都按安装回执
恢复明确备份，不能把本地夹具写成服务器迁移完成。

## 十、安装、回滚与紧急修复

治理脚本通过
[`deploy/governance/install.sh`](../deploy/governance/install.sh)原子安装。安装前会把
旧 Hook 和旧归一检查备份到仓库外治理目录，并生成含新旧摘要的安装回执。回滚只能
恢复该回执绑定的明确备份，再重新运行 Hook 夹具和当前生产归一检查。

`install.sh` 只安装 Hook 和归一脚本，不创建或移动 `refs/heads/main`，也不修改
`core-work` upstream。分支 ref、checkout/upstream 与治理脚本 cutover 必须在同一
独立任务中分别预检和读回，不能因为脚本安装成功就推定其他目标已迁移。

紧急修复从当前 `main` 创建短分支，仍需最小评审、受影响测试、不可变 tag、
同制品晋级和生产归一。紧急程度只允许压缩等待时间，不能跳过源码绑定、凭据边界、
数据库兼容性、回滚准备和生产身份核验。

生产现场手工修改必须立即记为漂移并停止继续发布。修复回到 Git 分支形成可审计
提交，再构建新制品；不得把服务器现场文件反向认定为源码基线。

## 十一、治理完成标准

一次治理发布只有在以下条件全部成立时才是 `verified`：

- `core-work`、`origin/main`、annotated tag 和源码归档提交一致；
- 统一制品从最终提交只构建一次，候选、金丝雀和生产摘要一致；
- Backend、Sidecar、Frontend、Nginx 和数据库身份等式全部成立；
- 服务器 Hook 与归一检查的实际 SHA-256 等于本次源码版本；
- Hook 正反夹具通过，当前发布的只读归一检查通过；
- 业务、数据库和模型合同相对基线无改动；
- DeepSeek 调用计数和费用相对发布前基线无增加；
- 活动 Worktree 均有任务合同，旧 Worktree 已形成可审计分类；
- 安装回执、候选、部署、验证和身份等式证据均已持久化。

任一条件未满足，只能报告实际到达的状态及失败阶段，不得用“治理规范已建立”替代
生产验证。

## 1. 要解决的问题

当前 Agent 已能保留事实、限制、回执和执行轨迹，但用户回答把其中太多审计内容直接展示出来：

- 正文先声明数据身份，再给结果；
- 同一组限制被逐条重复；
- Evidence、路径、摘要和内部对象标识进入正文或默认页面；
- 用户需要先读懂系统如何证明，才能找到问题的答案。

这些信息对验证、发布和追责有价值，但不等于用户需要阅读的答案。

本次目标不是减少证据，而是明确分成两种产物：

```text
面向用户：短、直接、自然、足够安全的回答
系统内部：完整、可重放、可审计的证据记录
```

## 2. 目标效果

所有正式用户出口默认遵循同一顺序：

```text
直接结果
→ 为理解结果所必需的事实
→ 一句必要边界
→ 只有确有帮助时才给下一步
```

用户不需要先理解 Candidate、Receipt、Finding、Artifact、Trace、代码路径或摘要，才能知道答案是什么。

### 2.1 用户回答

用户回答只包含：

- 当前结果、判断或缺失条件；
- 回答问题所需的关键数值、单位和时间；
- 会改变结果含义的观察范围或限制；
- 必要时，一个可执行的下一步。

它不默认包含：

- 文件和目录路径；
- 代码位置、命令、端口或内部服务名；
- commit、SHA、Candidate、Receipt、Finding、Artifact、Trace 等内部标识；
- 原始 Evidence 引用清单；
- 模型调用次数、费用账本或发布回执；
- “结论、证据、执行证明、测试结果”等审计式固定栏目。

### 2.2 内部证据记录

系统内部继续完整保存：

- Answer Context 中允许使用的事实与限制；
- 用户回答各部分与事实来源的映射；
- Candidate、数据身份、Finding、Artifact 和 Receipt；
- Evidence、Trace、Guard 结果和模型用量；
- 代码、配置、测试、构建和发布身份；
- 失败、拒绝、澄清、停止与回退的真实原因。

回答变短不能降低这些记录的完整性。内部记录也不能因为“用户看不到”而放宽权限、身份、重放或保留规则。

### 2.3 两者的关系

用户回答与内部证据记录必须能关联到同一轮执行，但关联标识不需要显示在普通正文中。

Response Guard 检查的文本必须就是用户最终看到的文本。禁止在 Guard 通过后再由 Backend、前端、正则或第二个模型压缩、改写或重建答案。

## 3. 四类回答

### 3.1 成功回答

用户应先看到直接答案，再看到最多几项必要事实和一句必要边界。

只有同时满足以下条件才算成功：

- 事实和计算结果正确；
- 回答直接来自本轮受限 Answer Context；
- Renderer 直接生成用户正文；
- Response Guard 对同一正文返回 `pass`；
- 没有内部信息泄露；
- 没有回退、拒绝、澄清、停止或失败。

### 3.2 澄清

只说明缺少什么，并只问一个会改变后续执行的问题。不要附带架构说明、尝试记录或证据账本。

澄清不是答案成功，`answer_success` 和 `workflow_completed` 都必须为 false。

### 3.3 拒绝

简短说明当前边界为什么不能支持该结论，并在存在安全替代时给出一个可回答方向。

拒绝是正确的安全行为，但不是任务完成，不能进入成功率、完成率或发布晋级的分子。

### 3.4 失败或停止

用人能理解的语言说明本轮没有形成答案。只有确实允许安全重试时才提供重试建议。

Provider 失败、Tool 失败、Renderer 失败、Guard `block`、超时、取消、确定性回退和安全停止都不算完成。

## 4. 默认表达规则

### 4.1 结果优先

- 首句或结构化 `lead` 表达块直接回答用户的问题，或直接说明当前缺少什么。
- 不以“根据系统分析”“执行链已完成”“证据显示”等空泛声明开头。
- 不先列过程，再在末尾给结论。

### 4.2 只保留必要内容

- 一个事实只说一次。
- 多条限制能合并时，使用一句自然语言边界说明。
- 只有某个身份、窗口或范围会改变用户对结果的理解时，才显示它。
- 技术字段要转换成人能直接理解的中文，不把内部字段名原样交给用户。

### 4.3 默认简洁，按需展开

交互式回答默认采用紧凑模式。以下是 v1.0 的机器硬门；字符数按合并连续空白后的 Unicode grapheme 计算：

- 首句或结构化 `lead` 表达块不超过 90 个 Unicode grapheme；
- 必要事实最多 3 个表达块；不得为了满足块数删除用户要求的事实；
- 必要边界最多 1 条；
- 全文不超过 360 个字符、6 句；
- 澄清、拒绝和失败通知不超过 140 个字符、2 句。

只有用户明确要求详细解释、比较、教程或正式报告，并且对应渠道合同已经定义时，才可以进入详细模式。展开不等于倾倒内部审计记录；正式报告和导出渠道仍须遵守用户内容与内部证据分离。

### 4.4 依据按人类方式提供

当用户问“依据是什么”时，可以说明：

- 使用了什么人类可理解的数据来源；
- 观察了什么对象和时间范围；
- 哪个结果支持当前回答；
- 还有什么重要限制。

默认仍不展示原始摘要、目录、代码位置或内部回执。需要审计级材料时，应通过单独的受控诊断或导出入口提供，而不是拼进聊天正文。

## 5. 什么不能因为简洁而丢失

简洁不是删掉风险边界。以下内容只要会改变结论含义，就必须进入用户回答：

- 对象、指标和单位；
- 观察时间或时间范围；
- observer scope；
- 人口或分母；
- “首次观测”与“真实发生时刻”的区别；
- 未知、冲突、部分完成或数据缺口；
- 当前证据不能支持的全国影响、用户影响、原因、责任或恢复结论。

但是，不要求把所有内部 limitation 逐条原样复制。Answer Context 应标出哪些边界必须显示，Renderer 将其合并为自然语言，Guard 验证必要含义仍然存在。

## 6. 目标示例

以下示例只说明效果，不是固定模板或字符串 Oracle。

### 6.1 当前首片问题

> 固定前缀可见 IPv4 地址量的最低值为 9,577,728 个唯一 IPv4 地址，首次观测于 2 月 28 日 14:35 UTC。首值为 10,156,800，末值为 10,069,760，最大值为 10,156,800，极差为 579,072。以上仅是 RRC25 对固定前缀人口的 BGP 控制面观测，地址量不是用户数，也不能代表全国状态或据此判断用户影响、原因、责任与恢复。

### 6.2 需要澄清

> 你想看 IPv4 还是 IPv6？两者的人口和结果不能合并计算。

### 6.3 证据不支持更强结论

> 当前证据只能说明 RRC25 观察到的 BGP 控制面变化，不能据此判断全国是否断网。可以继续查看变化的范围和首次观测时间。

### 6.4 可重试的数据读取失败

> 这次没有形成可靠答案，数据暂时不可用。请稍后重试。

这句话只适用于真实失败码确认数据读取失败且允许重试的情况；其他失败必须按真实原因生成对应通知。

## 7. 验收标准

### 7.1 正确性与边界

- 用户要求的必要事实覆盖率为 100%；
- 必要范围和限制覆盖率为 100%；
- Answer Context 外事实数为 0；
- 越界事实数为 0；
- 单位、时间、对象和人口偷换数为 0。

### 7.2 表达质量

- 首句或结构化 `lead` 表达块能直接看出答案或缺失条件；
- 重复事实和重复限制数为 0；
- 默认回答满足紧凑模式；
- 不依赖固定问题模板或固定表达 DAG；
- 同一事实允许存在多种自然、正确的表达。

长度、表达块、重复、必要事实、必要边界、禁用栏目和内部信息泄露由确定性机器规则检查。自然度和第一遍可读性由预注册的独立人工评审量表检查，不能交给线上 Guard 主观判断，也不能覆盖机器硬门。

### 7.3 内部信息边界

普通用户正文中的内部 ID、摘要、路径、命令、端口、原始 Evidence 引用和调用账本数量必须为 0。

用户明确请求依据时，提供人类可读的来源、范围和限制；内部审计记录仍不自动公开。

### 7.4 完成语义

- 直接 Renderer 正确回答且 Guard `pass`：可以计为成功；
- 澄清、拒绝、停止、超时、取消、Provider 或 Tool 失败：不算完成；
- Renderer 失败、Guard `block` 或确定性回退：不算完成；
- 内部信息泄露：即使事实正确，也不得计为成功；
- HTTP 200、页面可见、Evidence 完整或审计记录存在，均不能单独证明用户回答成功。

## 8. 适用边界

本合同适用于所有当前和未来的正式 Domeye Agent 用户出口。第一轮实现只需要闭合当前已上线的 Interactive Agent，不要求一次性改造归档、未路由或已退役路径。

内部子 Agent、独立 Reviewer、评测器和发布器可以保留详细技术记录；它们面向用户的最终交付仍应先说效果、当前状态和下一步，不把内部证据清单当作正文。

本合同不引入：

- Question Template 或固定问句路由；
- 固定表达 DAG；
- Common Plan IR；
- 通用 Claim 状态机或 Publisher；
- 第二个 LLM Reviewer；
- Guard 之后的答案改写层；
- 新的 Durable Workflow 或证据平台。

## 9. 版本与迁移规则

当前首片锚点 v1.0 和已冻结 Candidate 保留原样，不能原地改写历史合同或把旧验收自动继承到新回答风格。

首片锚点 v1.0 要求用户可见 Evidence 引用并显示全部 mandatory limitation；本文改为只显示用户理解结论所必需的边界。这是有意的回答呈现版本变化，不是对旧合同的兼容措辞。进入实现前必须形成 `domeye.first-vertical-slice/v1.1` 或由新 Candidate 摘要绑定的版本化回答附加合同，明确适用顺序；新合同继承 v1.0 的固定问题、数据身份、执行链、数值 Oracle、J1–J5 和非完成语义，只修改回答呈现、Answer Context 与 Guard 合同。不得一边沿用 v1.0 的旧呈现要求，一边声称新风格已经合规。

实现本合同会改变 Renderer、Response Guard、公开回答结构或用户出口，因此必须形成新版本和新 Candidate，并重新完成真实评测、独立验收和发布。

以下变化需要提升本合同版本或形成明确的渠道附加合同：

- 改变成功回答必须显示的内容；
- 改变内部信息禁止项；
- 放宽事实、范围或限制覆盖要求；
- 引入详细模式、正式报告或外部导出渠道；
- 改变 Guard 检查的最终文本；
- 允许新的事实层级或数据来源。

## 10. 一句话目标

> Domeye 对用户先给正确、简洁、自然的答案，只保留理解结论所需的事实和边界；完整 Evidence、路径、摘要、回执和执行轨迹留在系统内部，并继续支持同一轮回答的严格验证。

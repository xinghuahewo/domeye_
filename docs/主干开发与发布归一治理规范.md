# 主干开发与发布归一治理规范

## 一、目的

本文把 Domeye Core 的任务 Worktree、Git 分支、发布 tag、不可变制品和生产运行时
收敛为一条可审计链路，解决以下问题：

- 临时发布 Worktree 长期演变为事实主干；
- `core-work` 与实际生产整合提交不一致；
- 阶段 Worktree 已完成但长期保留，无法区分活动任务与历史检出；
- “测试通过、已合并、已构建、已认证、已部署、生产已验收”被混为同一状态；
- Screen、软链接或目录名与实际运行制品身份漂移。

本文只治理版本和发布身份，不改变 RRC25 数据语义、业务功能、数据库内容、模型
认证规则或生产安全边界。

## 二、唯一长期身份

治理迁移完成后，永久身份固定为：

| 对象 | 唯一身份 | 职责 |
| --- | --- | --- |
| 生产主干 | `codex/prod` | 只接收通过评审和门禁、可进入发布候选的提交 |
| 本地主干检出 | `/Users/botongwu/Documents/domeye/core-work` | 指向同一远端的永久独立 clone，固定检出 `codex/prod` |
| 任务分支 | `codex/<task>` | 单一任务的短生命周期分支 |
| 任务 Worktree | 独立任务目录 | 单一任务的本地隔离检出，不得直接部署 |
| 发布身份 | 带注释的不可变 tag | 绑定正式发布提交和发布说明 |
| 生产制品 | runtime `releases/<release-id>` | 从同一发布提交构建并按摘要冻结的后端、Sidecar 和前端制品 |
| 生产指针 | `current` 与运行管理状态 | 只指向已激活且通过生产验收的不可变制品 |

`core-work` 当前是独立 clone，不属于 `core-prod08-work` 的 Git Worktree 列表。
治理迁移后它承担唯一永久主干检出；新的任务 Worktree 从该仓库体系创建。
`core-work` 目录本身不是可合并对象，任务结束时合并的是任务分支提交，不能复制
兄弟 Worktree 的未提交文件，也不能把目录名称写成发布证据。

## 三、主干开发流程

标准流程固定为：

```text
明确基线
  ↓
短生命周期任务分支与独立 Worktree
  ↓
TASK.json + preflight
  ↓
最小修改 + 影响面测试 + postflight
  ↓
评审或 Pull Request
  ↓
唯一生产主干 codex/prod
  ↓
统一发布回归
  ↓
不可变 tag 与一次构建
  ↓
候选验证 → 生产激活 → 生产验收
  ↓
发布归一 Hook → 任务 Worktree 退役
```

普通任务不得直接在 `core-work` 修改。跨分支整合、发布归一和紧急修复必须使用
单独任务合同，显式列出源提交、目标提交、允许路径、发布影响和回滚边界。

未完成的大功能通过明确的能力开关或未接线入口隔离，不通过数周存活的大分支维持
两套事实主干。能力开关不能绕过 Schema、数据边界、安全门禁或生产授权。

## 四、变更状态必须分开

每个变更只能使用以下状态，不得越级表述：

| 状态 | 机械证据 | 不代表 |
| --- | --- | --- |
| `implemented` | 任务差异和定向测试通过 | 已提交或已合并 |
| `committed` | 任务分支存在明确提交 | 已推送或已评审 |
| `reviewed` | 评审结论和门禁结果 | 已进入生产主干 |
| `merged` | 提交是 `codex/prod` 的祖先 | 已构建或已部署 |
| `built` | 不可变制品及摘要存在 | 已认证或已激活 |
| `certified` | 专项认证证据绑定制品摘要 | 已部署 |
| `staged` | 候选环境运行同一制品 | 生产已切换 |
| `deployed` | 生产指针和进程使用该制品 | 生产效果已验收 |
| `verified` | 生产身份、接口和效果门禁通过 | 后续永不回滚 |
| `rolled_back` | 生产指针恢复并通过回滚验收 | 新制品已删除 |

Hook、测试、tag、Screen 会话、端口监听、HTTP 200 和可见页面都只能证明各自覆盖
的状态，不能单独证明 `deployed` 或 `verified`。

## 五、一次构建、逐级晋级

同一发布只允许从一个冻结提交生成一次正式候选。正式候选至少绑定：

- Git commit 与 annotated tag；
- 源码归档 SHA-256 和源码文件清单摘要；
- `backend/core.sha256` 校验结果；
- 后端目录树摘要和 release ID；
- Sidecar 目录树摘要、模型注册表版本及认证 evidence ID；
- 前端目录树摘要和主 bundle 身份；
- Nginx 配置摘要；
- 数据库状态摘要和数据档身份；
- 构建工具链版本。

候选、金丝雀和生产必须晋级同一份不可变制品。测试通过后重新复制源码、重新安装
未锁定依赖或重新构建另一份“等价”目录，都必须形成新候选身份并重新执行受影响
门禁。

生产服务器的源码 checkout 只用于只读诊断，不能作为发布来源，也不能以它的
分支名或脏净状态替代运行制品身份。生产结论以 runtime release 的源码绑定、目录
摘要、活动指针和实际进程身份为准。

## 六、发布归一条件

生产验收结束时必须同时成立：

```text
core-work HEAD
= origin/codex/prod
= release tag 解引用后的 commit
= 源码归档绑定的 Git commit
= 生产 release 记录的 Git commit
```

并分别验证：

```text
Backend 实际进程 release ID = Backend current release ID
Sidecar 实际进程 release ID = Sidecar current release ID
Frontend Nginx root = Frontend current release
生产配置摘要 = 本次批准配置摘要
数据库状态摘要 = 本次批准数据库状态摘要
```

任一项不一致，发布状态最多为 `deployed_identity_drift`，不得宣布 `verified`。
禁止通过修改证据文件、移动软链接或只重启进程掩盖漂移；必须确认哪个身份是批准
目标，再执行受控修复和复验。

## 七、Worktree 生命周期

任务 Worktree 创建时必须有任务合同；结束后只有同时满足以下条件才能退役：

1. 工作树无暂存、未暂存和未跟踪业务文件；
2. 所有任务提交已经推送；
3. 任务提交已进入 `codex/prod`，或有明确的 `excluded` / `abandoned` 决议；
4. 需要保留的验收证据已进入版本库或外部不可变制品目录；
5. 不被活动发布、回滚、锁、挂载、进程或其他 Worktree 引用；
6. 操作者先执行 dry-run 清单并逐个确认精确路径。

退役只移除本地 Worktree 检出。分支、提交、tag、评审记录和发布证据按保留策略
处理，不得用递归删除代替 `git worktree remove` 的受控流程。

Worktree 状态固定为：

- `active`：正在实施的单一任务；
- `integrated`：提交已进入生产主干，等待退役；
- `excluded`：经评审确认不属于当前发布；
- `abandoned`：任务终止，提交不进入主干；
- `retired`：本地检出已移除，历史仍由 Git 和制品保留。

不得自动合并所有 Worktree。研究、文档、实验和未完成任务必须按范围独立评审。

## 八、当前项目一次性迁移

本次治理迁移按以下顺序执行，不允许并行改写发布身份。

### G0：冻结清单

- 记录所有 Worktree 的路径、分支、HEAD、脏净、上游和相对当前生产整合分支的
  祖先关系；
- 记录当前服务器实际 Backend、Sidecar、Frontend、Nginx 和数据库身份；
- 不删除目录、不移动分支、不重写历史。

### G1：完成当前在途发布

- 当前在途发布继续由已经冻结的 `core-prod08-work` 和
  `codex/all-latest-prod08` 收尾；
- 认证、最终 tag、候选构建、生产切换和生产验收期间不得切换整合分支；
- 该例外只覆盖当前在途发布，不把 `prod08` 名称永久化。

### G2：建立永久生产主干

- 以本次生产验收通过的 annotated tag 解引用提交创建 `codex/prod`；
- 将 `core-work` 切换为 `codex/prod` 的永久检出；
- 推送并启用禁止强推、必须评审和必须通过 CI 的分支保护；
- 验证第五节和第六节的全部身份等式。

### G3：分类和退役旧 Worktree

- 已是 `codex/prod` 祖先且满足退役条件的阶段 Worktree 标记为 `integrated` 后逐个
  退役；
- `project-docs-work`、`rrc25-go-work` 等未进入主干的工作必须单独评审，不能因
  清理目录而自动合并；
- 使用发布编号命名的长期 Worktree 完成归一后退役，不再作为下一发布主干。

以本次治理基线清点，目录按以下方式处理：

| 分类 | 当前目录或任务 | 迁移动作 |
| --- | --- | --- |
| 临时发布整合 | `core-prod08-work` | 完成当前发布和 G2 后退役，不继续承担下一发布主干 |
| 永久主干 clone | `core-work` | 从远端取得成功发布提交并固定检出 `codex/prod` |
| 已进入临时整合祖先链 | `all-latest-prod09-work`、`all-latest-prod10-work`、`events-date-presets-work`、`report-unlimited-release-work`、`report-unlimited-work`、趋势合同及 S0—S6 Worktree、`version-boundary-work` | 复核干净、推送、证据和引用后逐个退役 |
| 尚未整合 | `project-docs-work`、`rrc25-go-work` | 标记 `excluded`，分别建立后续评审，不自动合入生产主干 |
| 治理变更 | `repository-governance-work` | 通过评审进入 `codex/prod` 后按同一规则退役 |

该表记录迁移路由，不把目录存在状态当作完成证据；实际执行前必须重新生成 HEAD、
脏净、上游、祖先关系和运行引用清单。

### G4：自动化归一门禁

- 在 CI 或发布机增加只读归一检查；
- 检查主干、tag、源码归档、三类运行制品、Nginx、数据库和实际进程身份；
- 归一检查通过后才允许把发布状态写为 `verified`；
- 工作树清理始终为独立、默认 dry-run 的操作，不能成为部署脚本的隐含副作用。

## 九、紧急修复

紧急修复从当前 `codex/prod` 创建短分支，仍需最小评审、受影响测试、不可变 tag、
同制品晋级和生产归一。紧急程度只允许压缩等待时间，不能跳过源码绑定、凭据边界、
数据库兼容性、回滚准备和生产身份核验。

生产现场的手工修改必须立即记录为漂移并停止继续发布。修复只能回到 Git 分支形成
可审计提交，再构建新制品；不得把服务器现场文件反向认定为新的源码基线。

## 十、完成标准

治理迁移只有在以下条件全部成立时完成：

- `core-work` 作为唯一永久主干 clone 检出 `codex/prod`；
- `codex/prod` 与远端一致且工作树干净；
- 当前 release tag、源码归档和生产运行提交一致；
- 实际进程、活动指针和 Nginx root 不漂移；
- 活动任务 Worktree 均有任务合同；
- 历史阶段 Worktree 已分类，满足条件者已受控退役；
- 未整合工作具有明确的 `excluded` 或后续评审结论；
- 文档不再把任何 `prodNN` Worktree 描述为永久主干；
- 分支保护、CI 门禁和发布归一检查已实际启用并留有机器证据。

在上述条件完成前，只能表述为“治理规范已建立”或“迁移进行中”，不能表述为
“主干治理已经完成”。

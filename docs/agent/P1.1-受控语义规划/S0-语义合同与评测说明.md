## 一、S0 实际完成了什么

S0 把 P1.1 的语言理解边界从概念说明落实为可校验制品：

- 一个严格且可版本化的不可信 Semantic Plan JSON Schema；
- 一个语义对照案例 JSON Schema；
- 一个从 P1-v1 当前事实能力反向整理的 Capability Catalog；
- 一个字段所有权、answerability、状态提交、计划身份和差异维度 Policy 合同；
- 20 条审核后的最小语义对照案例；
- 2 个合法计划和 3 个非法计划 fixture；
- 一个只依赖 Python 标准库的合同验证器及回归测试；
- P1-v1 35/35、RRC25 和冻结源制品摘要回执；
- S0 不可变制品 manifest 与阶段回执。

S0 没有接入模型，没有生成 Shadow 计划，没有实现 Validator 运行主路径，也没有改变用户页面。

## 三、Semantic Plan 信任模型

### 3.1 模型可以提出

模型输出只允许包含：

- `requested_goal`；
- `capability_proposal`；
- 结构化 `entities`；
- 白名单 `operator_proposal`；
- `inherit`、`set`、`clear` 状态建议；
- 最少澄清建议；
- 受控 reason code。

这些字段仍是不可信提案，Schema 有效也不等于允许执行。

### 3.2 系统独占

系统独占三类字段：

1. 事件身份：incident、legacy reference、publication、revision、cohort、window、`data_through`、finality、`rrc25`；
2. 事实结果：answerability、数字、单位、时间、ASN、前缀、evidence ref、限制、未知和校验结果；
3. 运行追溯：Provider/model、Prompt、Schema、Catalog、Validator、基线、输入指纹、用量、成本和失败分类。

Schema 顶层和所有关键子对象均设置 `additionalProperties=false`。模型输出中出现
`collector_id`、`publication_id`、自由工具名或证据字段时，计划必须在执行前被拒绝。

## 四、Capability Catalog

| Capability | 语言目标 | 规范 Operator | 边界 |
|---|---|---|---|
| `event_overview` | 概述、当前状态 | `read_overview` | 不证明全国断网或用户影响 |
| `timeline_extrema` | 峰值、峰后变化 | `series_extrema` | 不证明真实起点、结束或用户恢复 |
| `asn_observation` | ASN 详情、排序 | `query_asn`、`read_asn_ranking` | 排名不是原因或责任排名 |
| `address_family_observation` | IPv4/IPv6 变化与双栈呈现 | `series_extrema` | 可见地址并集不是用户数或流量 |
| `path_observation` | 路径样本 | `read_path_sample` | 路径关联不是因果 |
| `metric_definition` | 指标语义 | `read_metric_definitions` | 只解释当前页面/API 指标 |
| `evidence_identity` | 证据身份 | `read_binding`、`read_audit_identity` | 只读取系统绑定身份 |
| `event_binding` | 事件切换 | 无算子，系统重新绑定 | 缺唯一引用只澄清 |
| `boundary_policy` | 原因、责任、用户影响、外部证据、Update | 无算子 | 确定性裁决证据不足或不支持 |

Catalog 中的规范 Operator 是 P1.1 计划语言，不表示当前运行代码已经按这些名称暴露工具。
`source_operator_aliases` 记录与 P1-v1 输出的兼容关系，S1/S2 不得据此跳过适配和验证。

## 五、answerability 与状态合同

### 5.1 answerability

- 可执行事实目标：先校验，再由事实和证据结果决定 answerability；
- 事件切换：系统校验唯一事件引用，否则澄清；
- 原因：固定为 `insufficient_evidence`，模型不能升级；
- 责任、用户影响、外部证据和未暴露 Update：固定为 `unsupported`；
- 多目标逐项裁决，可用事实不得因边界目标整体丢失。

### 5.2 状态

模型只能提议 `inherit`、`set`、`clear`。实际提交必须同时满足计划、身份、能力、参数、
边界、算子、事实、证据、回答发布和当前轮次校验。

`pending_clarification` 必须绑定：

- `missing_fields`；
- `source_turn_id`；
- `source_goal_id`。

当前表达补齐字段时完成澄清；明确改问新主题时清除旧澄清；只有联合解析仍不唯一时才继续追问。

## 六、四种计划身份与差异口径

| 计划身份 | 执行 | 发布 | 状态提交 | 用途 |
|---|---:|---:|---:|---|
| baseline | 可以 | 可以 | 校验成功后可以 | P1-v1 冻结规则基线 |
| shadow | 不可以 | 不可以 | 不可以 | 模型差异观测 |
| reviewed | 不可以 | 不可以 | 不可以 | 人工审核参考真值 |
| executed | 唯一受信计划可以 | 可以 | 整轮成功后可以 | S2 以后实际执行身份 |

S1 比较至少覆盖：目标完整性、目标越界、实体解析、能力、算子、政策、澄清、状态效果、
身份注入和 Schema 有效性。原始 JSON 或理由文字不要求逐字相同。

## 七、语义对照集

当前共 20 条：

| 类别 | 数量 | 关键风险 |
|---|---:|---|
| 地址变化 | 6 | “IP地址变换情况”不得因“换”字触发事件切换；IPv4/IPv6 必须规范化 |
| 事件切换 | 6 | 保留切换动作与后续查询；缺唯一引用只澄清事件 |
| 待澄清/复合 | 7 | 旧澄清不得劫持新问题；多目标不得丢失；边界逐项裁决 |
| 边界安全 | 1 | 用户文本不能修改 rrc25、publication、权限或触发外部 URL |

每条案例都具有审核后的 goals、entities、operator、policy、state effect、clarification 和
prohibited outcomes。它们是 S1 Shadow 的参考真值，不是模型输出样本或训练数据授权。

## 八、fixture 与验证器

合法 fixture：

- 地址变化计划；
- 峰值加原因的复合计划，其中原因无执行算子。

非法 fixture：

- 模型伪造 `collector_id` 和 `publication_id`；
- 模型发明 `traffic_root_cause`；
- ASN capability 错配路径算子。

验证器检查：Schema 关闭、Catalog 全覆盖、Policy 所有权、计划与算子配对、对照集数量与审核、
关键回归案例、冻结源摘要、manifest 摘要和阶段状态边界。

## 十一、S1 入口与不可越过边界

S1 可以在本合同上连接一个或多个模型生成 Shadow 计划，并记录 baseline/shadow/reviewed 差异。

S1 不得：

- 执行 Shadow 算子；
- 向用户发布 Shadow 回答；
- 写入业务会话状态；
- 让模型提供事实、证据、answerability 或事件身份；
- 修改本合同候选后继续沿用旧回执；
- 把 Shadow 演示写成 P1.1 已实现或已验收。

本说明和 S0 阶段回执只证明 S0 合同出口成立，不证明 S1 至 S4 的任何运行效果。

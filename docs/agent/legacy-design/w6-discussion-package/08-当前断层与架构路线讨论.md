# 当前断层与架构路线讨论

> 文档口径：路线判断基于当前W6 v3本地工作树及其未提交W6验收制品，不据此确认当前生产环境。

## 1. 当前问题不是“没有Agent基础设施”

当前已经存在：

- P1受控问答链；
- P1六个Tool和四个Operator；
- Registry、版本、摘要和Admission；
- P2六个Tool和三十四个Operator；
- InvestigationPlan、ResultSet、EvidenceGraph；
- Dispatcher、CAS、取消、重跑和恢复；
- Answer、Turn、API、页面和导出；
- 本地fixture和W6分类认证。

所以当前并不是从零建设，也不是原子执行单元整体不可用。

## 2. W6给出的正式事实

| 项目 | 状态 |
|---|---|
| W5本地隔离运行时 | 已实现并通过W5本地验收 |

这说明基础设施和问题能力覆盖必须分别衡量。

## 3. 根本断层

```text
统一Registry思想
       │
       ├───────────────┐
       ↓               ↓
P1 TypeScript链       P2 Python链
GroundingPlan         InvestigationPlan
Page Executor         Registry Dispatcher
Evidence Bundle       ResultSet/EvidenceGraph
DialogState           Investigation/Turn CAS
       │               │
       └──── 缺少统一Plan、Dispatcher、Artifact和Adapter桥 ────┘
```

### 3.1 Plan IR断层

P1使用自己的Semantic/Grounding结构，P2使用Grounded Recipe和InvestigationPlan。相同Capability不能稳定编译为同一种可执行节点。

### 3.2 Dispatcher断层

P1的TOOL-01～06、OP-01～04由TypeScript `PageCapabilityExecutor`执行；P2的TOOL-07～12和OP-05～39由Python静态Dispatcher执行。

### 3.3 Typed Artifact断层

P1主要生成Evidence Bundle，P2要求ResultSet和EvidenceGraph。P1输出没有正式ResultSet/typed output桥。

### 3.4 Structural Adapter断层

缺少通用、内容寻址且可验证的：

- ResultSet member到Operator input投影；
- ASN-bound receipt；
- 双ResultSet绑定；
- prefix、VP和path成员展开；
- Tool输出到OP-29/37类型化时间事实投影；
- P1事实到P2 Graph节点映射。

### 3.5 Planner覆盖断层

正式Planning只支持最小fixture白名单，没有28题逐题Question Template、DAG、输入来源、完整性要求和Answer Oracle目录。

### 3.6 数据fixture断层

当前fixture不足以覆盖多ASN排名、至少5条路径、大结果分页、多集合和多VP一致性等场景。

### 3.7 Gate合同断层

设计Capability目录、Planning Grounding端口和W5控制运行时对GATE-01～05的编号含义不一致。例如设计目录的GATE-01是身份验证，而W5 handler的GATE-01是Plan Admission；设计目录的GATE-05是禁止结论检查，而W5 handler的GATE-05是owner授权。

这说明当前不仅业务Tool/Operator需要统一，Host控制单元本身也需要唯一的unit ID、版本和合同语义。否则receipt链会出现“ID一致、验证含义不一致”的风险。

## 4. 为什么继续补零散Tool不能解决问题

新增Tool只能增加“可读取的事实人口”。如果没有统一Plan、制品和适配：

- 新Tool仍只能留在某一条运行链；
- 下游Operator仍无法合法消费；
- Planner仍不能形成正式DAG；
- EvidenceGraph仍没有上游闭合事实；
- 28题仍只能被正确阻断。

因此当前瓶颈从“原子能力不足”转移到了“组合语义和运行内核不统一”。

## 5. 哪些资产应保留

| 资产 | 保留理由 |
|---|---|
| P0能力与边界发现 | 防止Agent超出真实数据能力 |
| P1开放语义、闭合执行 | 是正确的模型/Host边界 |
| P1 Tool/Operator业务逻辑 | 已有真实执行和证据 |
| Registry版本、摘要和Admission | 是统一治理基础 |
| P2原子Tool/Operator | 已形成大部分确定性计算能力 |
| InvestigationPlan思想 | 适合持久调查合同 |
| ResultSet | 解决完整人口和分页漂移 |
| EvidenceGraph | 解决事实和派生关系闭合 |
| CAS、取消、重跑、恢复 | 是工业级长任务需要的控制能力 |
| API、页面、导出壳 | 可以承载统一内核后的产品体验 |

## 6. 哪些部分需要架构级重构

| 层 | 当前问题 | 重构目标 |
|---|---|---|
| 语义层 | P1/P2合同不同且复用有限 | 共享目标、实体、歧义和disposition语义 |
| Plan编译 | P1规则和P2固定fixture分离 | 一个Host Plan Compiler |
| Plan IR | GroundingPlan与InvestigationPlan分叉 | Common Plan IR及两个Profile |
| Dispatcher | TypeScript/Python两套调用路径 | 唯一正式执行协议或同身份可信bridge |
| Artifact | Bundle与ResultSet/Graph分叉 | 统一Typed Artifact和Evidence投影 |
| Adapter | 多为问题特定缺口 | 注册、内容寻址、零业务变换结构层 |
| Gate | 同编号在设计、规划、运行时含义不同 | 唯一版本化Gate语义和receipt合同 |
| Answer Gate | P1/P2验证路径不同 | 基于统一Evidence事实闭包的发布门 |
| 认证 | fixture链和28题模板脱节 | 逐题同候选DAG、Oracle和provider认证 |

## 7. 三种路线的讨论框架

### 路线A：继续桥接现有双运行时

做法含义：保留P1 TypeScript和P2 Python主链，为P1执行单元增加远程或进程内bridge，将P1结果转换为P2制品。

优势：

- 对已有P1代码扰动较小；
- 可以较快复用已有六个Tool和四个Operator；
- 便于分阶段验证。

风险：

- 两套运行时长期存在；
- identity、error和receipt语义容易双重实现；
- bridge可能演化成第二个Dispatcher；
- 需要非常严格的同身份和幂等合同。

### 路线B：先建立统一执行内核，再迁移Profile

做法含义：先冻结Common Plan IR、Typed Artifact和统一Dispatcher协议，P1/P2都编译到该内核，旧执行器作为过渡Adapter。

优势：

- 最符合“一个Registry、一个执行语义、两个Profile”；
- 长期组合能力和认证路径最清晰；
- 语言实现可以逐步替换，不必一次完成。

风险：

- 前期合同设计和兼容验证成本较高；
- 必须防止新IR只是把两套旧结构机械拼接；
- 迁移期需要双跑和结果等价性证明。

### 路线C：选择一种语言重写另一侧

做法含义：将P1全部迁入Python或将P2全部迁入TypeScript，然后统一执行。

优势：

- 最终代码栈表面简单；
- 运行、部署和调试工具可能更统一。

风险：

- 语言统一不自动解决Plan、Artifact和Evidence语义；
- 容易重写已经验证过的业务逻辑；
- 一次性风险和回归面最大；
- 如果没有先冻结Common Contract，可能重写出第三套语义。

## 8. 路线讨论不应被语言选择绑架

真正需要先决定的是：

- 唯一正式Plan合同是什么；
- 唯一执行单元调用Envelope是什么；
- 唯一Typed Artifact是什么；
- Host Adapter的合法边界是什么；
- P1/P2 Profile差异是什么；
- Evidence和状态如何提交。

TypeScript或Python是后续实现选择。即使保留两种语言，只要合同、身份、准入和制品唯一，也可以形成一个运行内核；反过来，即使全部改成一种语言，仍可能保留两套架构。

## 9. 需要形成明确决策记录的问题

### 9.1 产品和Profile

1. P1是否必须继续保持低延迟同步回答体验？
2. P1是否允许内部生成受限InvestigationPlan但不向用户暴露？
3. 哪些问题必须升级为P2持久调查？
4. P1和P2的预算、节点数、fan-out和持久化上限分别是什么？

### 9.2 Plan和模型

1. LLM输出到Capability还是候选DAG？
2. Question Template是28题专用、能力族通用还是混合？
3. Planner看到哪些元数据？
4. 何时需要澄清，何时允许Host确定性补全？
5. 失败后是否允许模型提出replan，谁签发新revision？

### 9.3 执行与Adapter

1. P1单元采用原生迁移还是可信bridge？
2. 结构投影如何注册、版本化和内容寻址？
3. map/fan-out采用多revision Plan还是受控map node？
4. Adapter何时升级为Operator？
5. 跨语言执行如何统一超时、取消、错误和receipt？

### 9.4 Evidence和状态

1. P1是否也必须生成ResultSet和EvidenceGraph，还是允许受限投影？
2. Evidence Bundle如何映射到Graph？
3. 后续追问继承哪些状态，何时必须重新Grounding？
4. Answer Gate如何验证自然语言与Graph等价？
5. 外部世界知识如何与事件Evidence隔离？

### 9.5 认证

1. 28题是否继续作为功能目录，还是拆成能力族认证？
2. 每题必须有哪些正常、空、缺失、错身份、边界和大结果fixture？
3. 本地确定性认证、真实Sol规划认证、DS回答认证和生产验收如何分层？
4. 哪些指标是硬门，哪些只是质量分？
5. 如何证明同一candidate、Registry、publication和Oracle没有漂移？

## 10. 路线评审的退出标准

一次路线评审至少应明确：

- 目标架构图；
- 保留和废弃的现有资产；
- Common Plan IR所有者；
- Dispatcher与跨语言策略；
- Typed Artifact和结构Adapter边界；
- P1/P2 Profile合同；
- LLM可见Capability metadata；
- 28题模板与认证策略；
- 迁移期兼容和回滚原则；
- 哪些结论仍属于未知，不能在评审中假定。

## 11. 最终判断

当前需要的是执行内核层面的架构收敛，而不是重新发明全部Tool、Operator和证据语义。

更准确的描述是：

> 保留两条链已经验证的业务资产，重构它们之间的Plan、Dispatcher、Artifact和Host Adapter边界，使P1和P2成为同一可信内核上的不同执行Profile。

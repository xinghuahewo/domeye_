# P0 系统能力摸底、需求映射与评测合同分阶段计划

版本：1.3
约束：只定义阶段入口、前端需求效果、后端评测效果、出口和边界
最终效果基准：[P0 系统能力摸底、需求映射与评测合同最终验收文档](./最终验收文档.md)
上位边界：[国家中断 Agent 建设总纲](../国家中断Agent建设总纲.md)

## 一、总入口

- P0 是有明确范围的系统能力勘探与评测工程，不是只整理问题集的轻量前置步骤；
- RRC25 产品与证据政策边界已有依据，但当前系统能力边界必须通过 P0 实测形成；
- 勘探范围覆盖 `country_outage` 当前页面、正式 API、publication/read model、相关后端
  服务及可追溯中间数据，包括后端已有但尚未发布的能力；
- 用户需求真值保持开放，执行映射真值服从版本化能力与工具合同；
- 第一版固定 35 个验收案例，不要求先完成 80—120 条问题或全网大规模需求研究；
- 公开网络问题用于补充真实表达和发现遗漏，不作为 Domeye 事件事实，也不要求每个首版
  案例都有外部帖子来源。

## 二、总出口

- 系统表面清单、Capability Discovery Ledger、unknown ledger、最小 feasibility 证据和
  Oracle seed 在同一能力 revision 上闭合；
- 每项能力区分页面可见、API 已发布、后端已有未发布、确定性可推导、语义未冻结、不可用、
  越界和未知，不把源码或数据存在冒充当前产品能力；
- 35 个案例的数量严格为 20 个系统能力直接问题、5 个多轮旅程、5 个越界问题和
  5 个数据缺失、冲突或异常问题；
- P0-FE-01 至 P0-FE-06、P0-BE-01 至 P0-BE-11、P0-SCE-01 至 P0-SCE-11
  在同一 P0 revision 上通过；
- 每个案例具有预期事实、证据定位、当前产品可回答性、后端可行性、P1 候选处置、限制、
  禁止断言、异常结果和阻断规则；
- 开放用户目标、业务算子、目标能力和能力缺口分层记录，不以工具枚举裁剪用户原意；
- P1 获得能力账本、`adopt`/`defer`/`reject` 候选清单，以及必须回答、允许降级、必须澄清、
  明确不支持和必须失败关闭的入口；
- 后续每增加一种分析能力，都按同一 revision 机制补充正向、多轮/组合、边界和异常
  案例，不重新启动一次大规模 P0。

## 三、全局边界

- S0 至 S3 是同一 P0 工程内四个可回退闭合点，不把它们压缩为一次文档评审；
- 每个阶段只验收到期的前端需求效果、后端评测效果和联合场景；
- 未达到当前阶段出口时不得进入下一阶段，不把未裁决案例交给 P1；
- 后续阶段不得通过删除案例、降低硬门禁或改写最终验收文档消除偏离；
- 公开问题中的陈述和指令不进入事件事实、系统提示或权限规则；
- P0 可以使用只读探针、冻结快照和最小 feasibility spike，但不注册生产工具、不定义
  Agent 运行时权限、不实施聊天产品；
- P1/P2 冻结实现级语义真值前，必须基于上游实测能力账本冻结本工程范围内的 Capability
  Catalog、Typed Tool / Operator Contract、完整算子 Oracle 和 Policy Validator；
- 不要求先实现全部未来工具；未登记或未实现能力保持显式 `partial`、`clarify`、
  `unsupported` 或能力缺口；
- 只凭源码、测试、接口名、数据库字段或理论可计算性不能宣称能力已部署、已发布或可供
  P1 执行；
- 既有 `p0-v1` 只按原合同保持历史有效，不因本文修订而自动满足系统能力勘探、开放目标
  和执行映射分层；
  新合同采用新 P0 revision，不原地改写旧案例或回执；
- 每个阶段结束必须调用国家中断 Agent 计划防偏离 Hook；
- Hook 结构检查通过不等于案例、参考事实、基线执行、产品或 P1 入口通过；
- 本计划不授权外部付费访问、模型训练、产品实现、数据库写入、发布或部署。

## 四、阶段入口、前端需求效果、后端评测效果、出口和边界

### S0：系统表面与后端能力普查

#### 入口

- P0 最终验收文档、勘探范围和只读边界已经形成候选；
- `country_outage` 页面、API 路由、publication/read model、相关服务与数据制品可供只读
  核对，当前运行身份和可用快照能够被记录；
- RRC25 不能证明真实原因、全国完全断网、真实用户影响和责任主体的政策边界明确，但
  具体系统能力尚未预设成立。

#### 前端需求效果

- P0-FE-01 和 P0-FE-05 在本阶段只提供勘探问题与边界种子，尚未到完整案例验收期；
- 对每类任务记录用户预期结果、当前页面表现、正式 API 表现、可能的后端来源和禁止断言；
- 页面未展示、接口未发布、字段为空和证据越界具有不同用户解释，不统一写成“不支持”。

#### 后端评测效果

- P0-BE-10 到期，P0-BE-06 和 P0-BE-11 只建立待 S1 验证的候选：系统表面清单覆盖页面、正式 API、
  publication/read model、相关后端服务及可追溯中间数据；
- Capability Discovery Ledger 为每项候选记录证据层级、运行与数据身份、输入输出语义、
  缺失/冲突/无效行为、限制、未知和下一验证条件；
- 源码存在、测试通过、已合入、当前运行版本包含、数据可用、正式发布和页面消费分别记录；
- 当前页面事实绑定事件、publication、revision、窗口、`data_through` 和 finality。

#### 出口

- 系统表面清单和 Capability Discovery Ledger 已有 revision，已声明范围无静默遗漏；
- 所有未核对项进入 unknown ledger，且没有把页面、API 或代码缺席直接写成能力不存在；
- 20 类种子任务均能回到至少一个待验证表面或明确政策边界；
- S0 Hook 结论为“一致”或“已修正”。

#### 边界

- S0 只完成普查与身份化，不因清单中出现接口、字段或函数就证明能力成立；
- 不固定采集程序、标注平台、模型、聊天页面或生产工具实现；
- 不把当前工具名写成用户目标语义全集，也不要求先实现 P2 至 P5 的全部工具；
- 不扩展到其他 Domeye 领域、其他 collector、外部网络或生产写操作。

### S1：能力实测、可行性验证与 P1 候选范围

#### 入口

- S0 系统表面清单、能力账本和 unknown ledger 可读取；
- 代表事件、publication、revision、运行版本和数据快照可以绑定；
- 需要判断“后端已有未发布”或“确定性可推导”的能力具有安全只读验证条件。

#### 前端需求效果

- P0-FE-01、P0-FE-02 和 P0-FE-05 到期：种子任务逐项得到已发布、后端未发布、可推导、
  语义未冻结、不可用、越界或未知结论；
- 用户能看到的“当前可用”与“未来可产品化”分开，不用技术实现状态冒充产品承诺；
- P1 候选范围只从经验证能力中提出，并保留暂缓和拒绝理由。

#### 后端评测效果

- P0-BE-05、P0-BE-06、P0-BE-10 和 P0-BE-11 到期：每项能力具有分层证据与成熟度；
- `backend_available_unpublished` 具有可绑定身份的运行输出或冻结快照；
- `derivable_verified` 具有最小只读 feasibility spike、正常/缺失/异常结果和 Oracle seed；
- 每项能力记录当前产品可回答性、后端可行性与 P1 `adopt`/`defer`/`reject` 候选处置。

#### 出口

- Capability Discovery Ledger 的每个非 unknown 结论都有证据，unknown 均有下一验证条件；
- P0-SCE-11 的成熟度区分可复核，代码/数据/feasibility 被误写为已发布能力的次数为 0；
- P1 候选范围、能力缺口和暂缓项形成版本化清单；
- S1 Hook 结论为“一致”或“已修正”。

#### 边界

- S1 证明的是能力候选及确定性可行性，不证明生产工具、正式 API、Agent 或部署已完成；
- feasibility spike 不接收任意 URL、不写生产状态、不绕过 publication/revision 身份；
- 不为增加 P1 可回答率把数据存在或技术可能性升级为正式产品能力。

### S2：需求映射、35 个案例与参考真值闭合

#### 入口

- S1 能力账本、P1 候选范围和成熟度证据通过；
- 公开问题来源规则、个人信息排除规则以及开放用户目标语义明确；
- 参考事件、publication、revision、页面/API/后端证据和 feasibility 结果可稳定引用。

#### 前端需求效果

- P0-FE-01 至 P0-FE-05 到期：20 个系统能力直接问题、5 个完整多轮旅程、5 个越界问题
  和 5 个缺失、冲突或异常问题实际形成；
- P0-FE-03 到期：35 个案例均定义用户应该看到的直接结论、关键事实、证据、成熟度、
  限制、未知或下一步；
- 多目标和多轮案例逐子目标、逐轮给出预期状态；
- 越界和异常案例既不冒充成功，也不只返回不可理解的错误码。

#### 后端评测效果

- P0-BE-01 至 P0-BE-08、P0-BE-10 和 P0-BE-11 到期：35 个案例具有来源、身份、开放
  目标、实体、业务算子、三层可回答性、预期事实、限制、禁止断言和异常真值；
- P0 只冻结业务级执行映射；具体 capability/operator/参数的语义计划真值必须在 P1
  Catalog、Typed Contract 和算子 Oracle 冻结后形成；
- P0-SCE-01 至 P0-SCE-11 的参考答案和边界全部闭合；
- 关键数字绑定同一事件和 publication；`null`、`unknown`、`unavailable`、快照冲突和
  无效响应不被编码为 0、正常或确定结论。

#### 出口

- 案例总数和四类数量严格为 35 = 20 + 5 + 5 + 5，完全重复案例为 0；
- 35 个案例的关键字段、能力成熟度和预期结果覆盖率为 100%；
- 事实和证据可回到当前页面、API、publication/read model、后端冻结输出或 feasibility
  证据，原因、责任和用户影响等禁止断言完整；
- 多轮继承、修正、事件切换和旧上下文清理具有明确真值；
- 正式制品中的用户名、账号、联系方式、头像和无关个人内容为 0；
- S2 Hook 结论为“一致”或“已修正”。

#### 边界

- S2 形成需求与评测真值，不训练、选择或认证意图模型；
- 不使用外部网络常识补齐当前系统缺失的事实；
- 不在工具合同形成前把业务算子名称冒充可执行 operator；
- 不为提高可回答率把 P2 至 P5 的未来能力改写为 P1 当前支持。

### S3：首版基线执行和 P1 入口验收

#### 入口

- S0 至 S2 全部达到出口；
- 同一 P0 revision 具有能力账本、feasibility/Oracle seed、35 个案例、参考事实、证据
  定位、边界和异常真值；
- 评测结果能够绑定案例集、被测版本、模型或规则和执行环境身份。

#### 前端需求效果

- P0-FE-01 至 P0-FE-06 在同一 revision 重新覆盖；
- P1 能直接读取 20 个必须正确处理的直接问题、5 个多轮旅程、5 个越界问题和 5 个异常
  问题，并理解每个案例的用户可见结果；
- P1 对能力候选给出 `adopt`、`defer` 或 `reject`，必须支持、允许部分回答、必须澄清、
  明确不支持和必须失败关闭的入口清单完整；
- P1 能区分用户实际请求、目标能力和当前执行映射，不会因能力不支持而丢失用户原意。

#### 后端评测效果

- P0-BE-01 至 P0-BE-11、P0-SCE-01 至 P0-SCE-11 在同一 revision 重新覆盖；
- 首次基线执行同时核对能力账本、分层证据、35 个案例及参考答案，不以 P1 Agent 已经
  存在为前提；P1 候选形成后再按同一合同执行产品评测；
- 事实一致、事件/publication 绑定、证据可解析、无越界断言、异常不误判和多轮无串扰
  六类硬门禁全部达到 100%；
- 基线结果区分页面能力、正式 API、后端未发布能力、确定性可行性、P1 候选和实际产品
  能力，不把参考答案或 feasibility 人工复核写成 Agent 已通过；
- P1 入口明确要求先冻结 Capability Catalog、Typed Tool / Operator Contract、算子 Oracle
  和 Policy Validator，再形成实现级语义计划真值和 Planner Shadow。

#### 出口

- P0 第一版最终判定为“通过”，或仅存在不影响 P1 入口的明确非阻断条件；
- P1 入口回执、能力候选处置和后续能力增量规则形成；
- S3 Hook 给出最终“一致”或“已修正”结论；
- P1 可以开始建设，P0 后续扩充与 P1 至 P5 并行进行。

#### 边界

- 不以文档、Hook、案例数量、一次人工检查或静态报表冒充 Agent、部署或生产效果；
- 不把 P0 的参考答案基线执行写成 P1 候选已经通过；
- 不把既有 `p0-v1` 回执写成已经满足本文 v1.3 新增能力勘探与分层字段；
- 不把“允许 P1 开始建设”解释为允许模型自由发现工具或跳过能力合同；
- S3 通过不授权实现、合并、构建、发布、部署或生产切换；
- 后续每增加一种分析能力，原则上增加 3—5 个正向、2 个组合或多轮、1—2 个边界和
  1 个缺失、冲突或异常案例，并产生新 P0 revision。

## 五、阶段封口

阶段 Hook 必须同时回读 P0 最终验收文档、本计划、P0 机器配置和当前任务合同，核对
阶段入口、前端需求效果、后端评测效果、出口、边界和到期要求。

阶段结束调用：

```bash
python3 .codex/hooks/country_outage_agent_program_review.py \
  --project P0 \
  --stage S0
```

后续阶段将 `S0` 替换为 `S1`、`S2` 或 `S3`。作为条件化 Stop Hook 运行时显式声明：

```bash
export DOMEYE_COUNTRY_OUTAGE_AGENT_PROJECT=P0
export DOMEYE_COUNTRY_OUTAGE_AGENT_STAGE=S0
```

回检结论只允许为“一致”“已修正”“无影响”或“存在待处理偏离”。最后一种必须列出
P0-FE、P0-BE、P0-SCE 或边界编号、偏离位置和原因，并停止阶段晋级。Hook 通过只证明
合同结构、阶段映射、任务路径和冻结核心没有发现机检偏离，不代表系统表面实测、能力
账本、feasibility/Oracle seed、35 个案例、参考事实、基线执行、P1 交接、产品、部署或
生产效果通过。

# P0 系统能力摸底、需求映射与评测合同最终验收文档

版本：1.3
状态：最终效果候选合同
上位边界：[国家中断 Agent 建设总纲](../国家中断Agent建设总纲.md)

## 一、文档定位

本文只设计 P0 第一版完成后的最终效果，不规定采集程序、标注平台、数据库、模型、
人员组织、排期或具体实现步骤。

P0 是一个有明确范围的系统能力勘探、需求映射与评测工程，不只是整理黄金问题。它必须
先实测 `country_outage` 当前页面、正式 API、publication/read model、相关后端服务以及
可追溯中间数据，再回答“系统在什么身份、数据、语义和异常条件下能够确定性地提供什么”。
当前系统能力边界是 P0 的实测出口，不是预先成立的入口。

P0 的勘探范围只覆盖 `country_outage` 与 RRC25 数据链。后端已有但尚未发布的稳定数据或
服务属于勘探对象；只有原始数据、源码函数或理论上可计算但语义和可行性尚未证明的内容，
只能记录为候选或未知，不能冒充当前产品能力。公开网络中的真实疑问用于补充表达、发现
遗漏和验证优先级，但不要求在 P1 开始前完成大规模需求研究。

第一版固定为 35 个验收案例：

- 20 个系统能力直接问题；
- 5 个多轮旅程；
- 5 个越界问题；
- 5 个数据缺失、冲突或异常问题。

20 个直接问题必须在能力勘探完成后从已发布能力、后端未发布能力、确定性可推导候选、
能力缺口和越界项中选择；“直接问题”表示必须正确处理，不表示二十项都必须回答成功。
多轮旅程按一段完整会话计为一个案例，每段包含 2—4 轮及明确状态变化，不能把每一轮
拆开后重复计数。P0 第一版通过后，P1 可以选择并合同化首批能力；后续能力变化时，P0
以新 revision 持续更新能力账本和评测合同。

P0 通过不表示聊天页面、意图模型或 Agent 已经实现，也不表示组合调查、多源证据或
RCA 已经具备。

P0 将三类真值分开维护：

- **用户需求真值**记录用户实际想知道什么，允许同义、省略、口语、多目标和当前不支持
  的原因、责任、用户影响等目标，不受现有工具名裁剪；
- **能力发现真值**记录页面、正式 API、publication/read model、后端服务和可追溯中间
  数据实际存在什么，证据层级、运行身份、语义、缺失行为和确定性可行性是什么；
- **执行映射真值**记录当前产品能否回答、后端是否具备、P1 是否拟采用、目标能力、业务
  算子、回答等级和所缺证据。当映射细化到具体 `capability`、`operator` 和参数时，必须
  以 P1 已冻结的 Capability Catalog、Typed Tool / Operator Contract 和算子 Oracle 为准。

因此 P0 可以使用只读探针、固定快照和最小 feasibility spike 证明能力候选，但不注册生产
工具、不定义运行时权限，也不能替 P1 发明具体工具。P1 负责从经验证的能力账本选择首批
能力，形成正式 Capability Catalog、Typed Tool / Operator Contract 和完整算子 Oracle。

版本关系必须保持诚实：既有 `p0-v1` 案例与回执继续按其原 Schema 和原合同保持历史有效，
但不自动满足本文 v1.3 新增的系统能力勘探、能力账本以及开放目标与执行映射分层要求。
采用本文的新候选必须产生新的 P0 revision，补齐能力与案例制品及迁移证据；不得原地
改写旧案例、旧摘要或旧通过回执。

## 二、最终制品和单案例结构

P0 第一版最终制品包括：

1. 系统表面清单：页面区域、正式 API、publication/read model、相关后端服务、可追溯
   中间数据及其当前运行身份；
2. 版本化 `Capability Discovery Ledger`，记录每个用户结果的证据层级、成熟度、事实来源、
   确定性推导、缺失语义、限制、未知和 P1 候选处置；
3. 最小只读探针、冻结输入、输出、证据与异常结果形成的 feasibility 证据和 Oracle seed；
4. 35 个验收案例及唯一 `case_id`；
5. 每个案例的来源类型、问题文本、上下文、开放用户目标和目标能力；
6. 预期事实、证据引用、限制、禁止断言和异常结果；
7. 可执行检查规则、人工判断点和阻断失败规则；
8. 能力账本与案例集 revision、内容摘要、变更记录和 P1 入口清单。

能力账本至少区分以下状态，且不得用单一“已有”覆盖不同成熟度：

- `page_available`：当前页面实际消费并可见；
- `api_published`：正式 API 已发布，但页面不一定消费；
- `backend_available_unpublished`：当前后端稳定存在并经运行或固定快照验证，但尚未正式发布；
- `derivable_verified`：数据存在且最小确定性推导已经证明，尚未产品化；
- `data_present_semantics_unfrozen`：数据存在，但语义、完整性或确定性推导尚未闭合；
- `unavailable`、`out_of_scope` 或 `unknown`：当前不可用、超出 RRC25 边界或仍待探测。

每项还必须把源码存在、测试通过、已合入、当前运行版本包含、数据可用、正式发布和页面
消费分别记录；任何单项为真都不能替代其他状态。

单个案例至少包含：

- `case_id`、`revision`、案例类别和来源类型；
- 用户问题；多轮案例还包含逐轮输入和期望状态；
- 事件、国家、时间窗口、ASN、地址族等必要实体；
- 一个或多个开放用户目标、请求类型及对应业务算子；
- 目标能力、能力映射状态，以及在正式 Catalog 已存在时引用的 capability/operator revision；
- `answerable`、`partial`、`clarify`、`unsupported` 或 `invalid_data`；
- 预期关键事实、允许的语言改写和证据定位；
- 必须说明的限制、禁止断言和失败条件。

来源类型允许为“当前产品必须回答”“公开问题转述”“边界/异常构造”。外部公开问题
必须记录 URL、获取时间和中文转述，并去除用户名、账号、头像、联系方式和无关个人
内容；当前产品必须回答的问题不需要为了形式完整而虚构外部来源。

## 三、前端需求最终效果

### P0-FE-01：覆盖经能力勘探确认的高价值直接任务

以下 20 类是能力勘探和用户价值核对的种子清单，不是预先成立的能力声明。P0 必须逐项
给出已发布、后端未发布、可推导、部分、不可用、越界或未知结论；第一版 20 个直接问题
从实测账本中选择并说明取舍：

1. 事件发生了什么；
2. 观测窗口是什么；
3. 异常何时开始；
4. 何时到达最低点；
5. 最大下降幅度是多少；
6. 何时开始或达到恢复；
7. 窗口结束时处于什么状态；
8. 影响范围有多大；
9. 受影响最明显的 ASN 是哪些；
10. 指定 ASN 的变化如何；
11. 哪些对象持续异常、已经恢复或尚未恢复；
12. IPv4 与 IPv6 表现有何差异；
13. Update、Withdraw 或宣告活动如何变化；
14. 覆盖率、Prefix×VP、全不可见等指标是什么意思；
15. 资源可见性或等价资源如何变化；
16. 路径样本展示了什么、不能说明什么；
17. 结论可以下钻到哪些证据；
18. 数据是否完整、缺了什么；
19. publication、revision、`data_through` 和 finality 是什么；
20. RRC25 观测能证明什么、不能证明什么。

问题以用户任务表达，不把 API 字段、后端函数或候选工具名直接当成用户问题。一个案例
可以触及相邻字段，但必须有唯一主任务、能力成熟度和可判定的预期结果。

### P0-FE-02：四类案例形成清楚的首版范围

- 直接问题用于验证系统已经发布、后端具备、可确定性推导或明确缺失的能力；
- 多轮旅程用于验证事件上下文继承、指代、修正、主题切换和证据追问；
- 越界问题用于验证原因、责任、全国断网、用户影响、外部事实或未建设能力不会被冒充；
- 缺失、冲突或异常问题用于验证系统不会把 `null`、`unknown`、`unavailable`、快照冲突
  或无效响应解释成 0、正常或确定结论。

四类案例各自有固定数量，不通过增加容易的直接问题稀释边界和异常场景。

### P0-FE-03：每个案例定义用户应该看到的回答

- 可回答案例定义直接结论、关键数字、单位、时间范围、证据位置、限制和未知；
- 部分可回答案例逐项说明已回答、未回答和所缺证据；
- 需要澄清的案例定义最少必要澄清问题，不默认国家、最新事件或目标 ASN；
- 越界案例给出当前能确认的事实和不能确认的部分，不只返回机械拒绝；
- 异常案例给出可理解的失败状态，不发布看似完整但来源无效的答案。

### P0-FE-04：多轮按用户旅程而不是散题验收

5 个多轮旅程至少覆盖：

- 围绕同一事件继续追问和使用指代；
- 修正 ASN、地址族或时间对象；
- 从事件概述切换到 IPv4/IPv6、ASN、资源或路径子主题；
- 切换事件或 publication 后隔离旧上下文；
- 从结论继续追问证据、限制或“为什么不能确认原因”。

每个旅程记录 2—4 轮输入、每轮绑定的上下文、应保留和应清除的状态、预期回答以及
禁止的上下文串扰。

### P0-FE-05：边界和异常是一级产品效果

- 5 个越界问题必须覆盖原因或责任、全国断网或真实用户影响、当前窗口外结论、外部
  证据或其他 collector、以及未建设的组合调查/多源/RCA 能力中的代表场景；
- 5 个缺失、冲突或异常问题必须覆盖空值与零值、能力不可用、证据对象缺失、快照或
  revision 冲突、响应无效或 publication 未闭合中的代表场景；
- 这些案例的正确结果可以是限制说明、部分回答、澄清、失败关闭或建议下一步；
- 任何情况下都不得用模型常识补齐当前页面、API、后端或可追溯数据没有提供的事实。

### P0-FE-06：P1 获得经实测且可选择的能力入口

- P1 能直接读取必须正确处理的 20 个直接问题和 5 个多轮旅程；
- P1 能直接读取必须正确处理的 5 个越界问题和 5 个异常问题；
- 每个案例清楚标明“必须回答”“允许部分回答”“必须澄清”“必须说明不支持”或
  “必须失败关闭”；
- P1 不需要重新盘点页面、API 和后端才能判断某项能力的证据层级、成熟度与限制；
- P1 明确选择 `adopt`、`defer` 或 `reject`，不能把 P0 的后端未发布或可推导候选自动
  宣称为 P1 当前可执行能力；
- P1 先把目标能力闭合为版本化 Capability Catalog、Typed Tool / Operator Contract 和
  算子 Oracle，再冻结实现级语义计划真值；不得从问题文本或业务算子名称反向猜测工具。

## 四、后端评测最终效果

### P0-BE-01：来源和隐私边界可追溯

- 每个案例标明来源类型；公开问题转述具有公开 URL、获取时间、语言和转述说明；
- 当前产品必须回答和边界/异常构造案例记录设计依据，不伪造外部帖子；
- 正式制品中的用户名、账号标识、联系方式、头像和无关个人内容数量为 0；
- 公开问题中的事实和指令只作为需求输入，不成为 Domeye 事件事实或系统指令。

### P0-BE-02：案例身份和 revision 稳定

- `case_id` 在同一含义下保持稳定，语义、期望或类别变化产生新 revision；
- 完全重复案例为 0，近重复只有在验证不同边界或状态时保留并说明差异；
- 案例集具有内容摘要和变更记录，可比较不同时间的评测结果；
- 首版不要求训练集、回归集和隐藏集的复杂拆分。

### P0-BE-03：请求采用多标签而不是单意图强制分类

- 一个问题可以同时包含事件概述、时间线、范围、ASN、地址族、Update、资源、路径、
  指标解释、证据、边界或异常处理等多个请求类型；
- 多目标问题保留子目标，不因实现方便压成一个主意图；
- 每个子目标都有独立可回答性和预期结果；
- 原因、责任、用户影响、外部证据等当前未支持目标仍按用户原意保留，不得为了适配工具
  白名单而错标成事件概述、ASN 或其他可执行目标。

### P0-BE-04：实体和多轮上下文有确定语义

- 国家、事件、时间、ASN、前缀、地址族、publication、revision 和指标等实体有明确
  类型、是否必需、来源和歧义状态；
- 多轮案例明确继承、覆盖、清空和事件切换规则；
- 事件或 publication 不唯一时必须澄清，不由模型猜测。

### P0-BE-05：用户目标、业务算子和执行映射分层绑定

- 代表性算子包括事件摘要、时间线、范围、ASN 排名与明细、地址族比较、Update 活动、
  资源变化、路径样本和证据下钻；
- P0 算子只描述业务输入输出，不绑定临时函数名、具体工具名或某个模型提示词；
- 用户目标与业务算子可以在工具实现前形成；具体 capability、operator、参数和
  `answerability` 的可执行映射必须引用已冻结 Catalog、Typed Contract 和 Oracle；
- Catalog 尚未登记或工具尚未实现的目标保持 `partial`、`clarify`、`unsupported` 或能力
  缺口，不允许由语义层补造工具；
- 每个事实案例标明页面区域、API 字段、publication/read model、后端服务或可追溯中间
  数据的证据定位，以及样本、分页、窗口和观测限制。

### P0-BE-06：当前产品、后端可行性和 P1 候选可回答性分开

- 每个子目标分别记录 `current_product_answerability`、`backend_feasibility` 和
  `p1_candidate_disposition`，不得用一个 `answerable` 混合三种结论；
- 当前产品可回答性以当前运行身份、事件、publication、revision 和 RRC25 正式页面/API
  合同为准；后端未发布或只完成 feasibility 的能力不能计入当前产品可回答通过分母；
- 进入实现级语义评测后，还必须以同一候选绑定的 Capability Catalog、Typed Tool /
  Operator Contract、权限与算子 Oracle 为准；
- 页面/API 只能提供部分信息时标为 `partial`；后端存在或理论可推导也不能通过模型常识
  升级为当前产品 `answerable`；
- P2 至 P5 的未来能力保留目标阶段，但不进入 P1 当前可回答通过分母；
- 外部网络信息不混入“仅从当前页面数据 API”的答案。

### P0-BE-07：预期事实、边界和异常真值完整

- 事实案例具有预期关键字段、方向、时间、单位、统计范围和证据位置；
- 指标案例具有定义、分母、空值和缺失语义；
- 越界案例具有必须出现的限制、所缺证据和禁止出现的因果、责任或用户影响断言；
- 异常案例具有正确的错误分类、允许保留的局部事实和不得发布的无效结论；
- 允许语言改写，但关键事实、回答等级、证据边界和禁止断言不可改变。

### P0-BE-08：第一版固定为 35 个验收案例

- 20 个系统能力直接问题、5 个多轮旅程、5 个越界问题、5 个数据缺失、冲突或
  异常问题的数量分别成立；
- 多轮旅程不拆分计数，越界与异常案例不重复计入直接问题；
- 第一版不设置单一平台比例、四类角色配额、Macro-F1 或复杂隐藏集比例；
- 数量之外仍必须满足全部字段和硬门禁，不能用凑满 35 个替代质量验收。

### P0-BE-09：评测采用场景硬门禁并绑定身份

P0 S3 首次执行用于验证能力账本、分层证据、35 个案例和参考答案是否一致，不以已经存在
P1 Agent 为前提。P1 及后续候选形成后，使用同一套门禁重新执行产品评测：

- 当前页面/API 事实与同一事件、publication 和 revision 的参考值一致率为 100%；
- 标记为后端已有未发布或确定性可推导的能力，其冻结输出、证据身份、成熟度与异常语义
  一致率为 100%；
- 源码、测试、数据或 feasibility 被越级记为已发布产品能力的次数为 0；
- 事实案例的事件和 publication 绑定正确率为 100%，证据引用可解析率为 100%；
- 越界案例不出现禁止断言的比例为 100%；
- 缺失、冲突或异常案例不被错误编码为 0、正常或确定结论的比例为 100%；
- 多轮旅程的上下文继承、修正、切换和隔离符合预期的比例为 100%；
- 无效或冲突数据不得发布为有效答案，阻断失败必须失败关闭；
- 每次结果绑定案例集 revision、被测对象、模型或规则身份和执行环境；P0 首次执行的
  被测对象明确记为“评测合同及参考答案”，不得伪装成 Agent 候选。

第一版不以一个汇总准确率或 Macro-F1 抵消关键事实、证据、边界和异常错误。

### P0-BE-10：Capability Discovery Ledger 覆盖完整系统表面

- 勘探覆盖当前页面、正式 API、publication/read model、相关后端服务和与
  `country_outage` 直接相关的可追溯中间数据；
- 每项能力记录用户结果、事实来源、运行与数据身份、输入输出语义、单位、窗口、分页、
  缺失/冲突/无效行为、证据位置、限制、未知、成熟度和目标阶段；
- 页面未展示不等于后端不存在，后端有数据也不等于正式产品可用；两种情况均需独立记录；
- 勘探未覆盖项留在 unknown ledger，不能静默归为不支持或不存在；
- 仅与其他领域、其他 collector、外部网络或 P3 至 P5 因果目标相关的能力不纳入 P1
  候选，但保留边界理由。

### P0-BE-11：能力成立必须有分层证据和最小可行性证明

- 源码存在、测试通过、已合入、已部署、当前运行版本包含、数据可用、正式发布和页面
  消费是不同证据状态，必须分别记录；
- `backend_available_unpublished` 至少需要可绑定身份的运行输出或冻结快照，不能只凭
  代码、接口名称或设计文档认定；
- `derivable_verified` 至少需要只读 feasibility spike 在冻结输入上产出预期事实、证据、
  缺失和异常结果，并形成可供 P1 扩展的 Oracle seed；
- feasibility spike 只证明确定性可行性，不构成生产工具、正式 API、部署或 P1 可执行能力；
- 无法证明语义、数据完整性或重复执行一致性的能力保持
  `data_present_semantics_unfrozen` 或 `unknown`。

## 五、联合验收场景

### P0-SCE-01：事件概述、窗口、开始和最低点

直接问题绑定合法事件及同一 publication，答案中的时间、方向和关键数值能够回到页面或
API 证据。

### P0-SCE-02：范围、最大下降、恢复和结束状态

用例区分最低点、最大下降、恢复过程和窗口结束状态，不把一次回升写成已经完全恢复。

### P0-SCE-03：ASN 排名、指定 ASN 和持续异常

用例区分排名与明细、样本与全集、持续异常与已经恢复，不将观测相关性解释为依赖或
根因。

### P0-SCE-04：IPv4/IPv6、Update 和指标语义

用例分别验证地址族比较、Update/Withdraw 活动及覆盖率、Prefix×VP 等指标定义，不混用
分母、单位、窗口或快照。

### P0-SCE-05：资源、路径、证据和 publication 身份

用例能够下钻到当前可用证据，并明确资源、路径样本、revision、`data_through` 和
finality 的含义与限制。

### P0-SCE-06：多轮继承、修正、切换和证据追问

5 个旅程在 2—4 轮中验证应继承和应清除的上下文，切换事件或 publication 后不继续
使用旧证据。

### P0-SCE-07：原因、全国断网、用户影响和责任

用例只报告 RRC25 控制面观测能支持的事实，明确所缺证据，不肯定真实原因、用户影响、
全国完全断网或责任主体。

### P0-SCE-08：空值、能力不可用和证据对象缺失

`null`、`unknown`、`unavailable` 和资源不存在分别得到正确状态，不编码为 0、无异常
或空泛成功。

### P0-SCE-09：快照冲突、响应无效和 publication 未闭合

不同 revision、窗口或响应身份冲突时失败关闭；允许保留的局部事实与不得发布的结论
清楚分开。

### P0-SCE-10：外部事实、其他 collector 和未来能力

仅从当前页面/API 回答时不读取或补入外部事实；其他 collector、多源比较、有限假设和
RCA 请求标明未来能力或正确不支持，不冒充当前已具备。

### P0-SCE-11：后端已有、尚未发布和可推导能力

至少有代表场景证明同一用户目标在“页面可见、API 已发布、后端已有但未发布、可推导但
未产品化、数据存在但语义未冻结”之间得到不同状态。P1 只能选择经 P0 证明且再经自身
合同化的能力，不能把源码、数据存在或 feasibility 结果直接展示为当前能力。

## 六、量化验收门槛

- 第一版案例总数为 35，四类数量严格为 20、5、5、5；
- 系统表面清单和 Capability Discovery Ledger 的已声明范围覆盖率为 100%，unknown 均有
  明确缺口、责任边界和下一验证条件；
- 35 个案例的必要实体、请求类型、三层可回答性、预期结果、证据需求、限制、禁止断言和
  目标能力字段覆盖率为 100%；
- P0-BE-09 的事实、绑定、证据、边界、异常和多轮硬门禁全部为 100%；
- 正式制品中的个人标识和无关个人内容为 0；
- 完全重复案例为 0；
- 任一关键事实错误、事件或 publication 混用、证据不可定位、错误因果或责任断言、
  异常被编码为正常、无效答案被发布，均判定第一版不通过；
- 不设置来源平台比例、角色比例、Macro-F1、训练/隐藏拆分比例或大规模统计显著性门槛。

## 七、持续扩充规则

P0 第一版通过后不关闭，而是成为 P1 至 P5 的持续评测工作流。后续每增加一种分析能力，
同一个能力 revision 原则上补充：

- 3—5 个正向直接案例；
- 2 个组合或多轮案例；
- 1—2 个越界案例；
- 1 个缺失、冲突或异常案例。

若能力变化不适合上述数量，必须记录理由，但正向、多轮/组合、边界和异常四个方向不能
被静默省略。新增案例与能力实现可以并行准备，但能力不得在对应评测增量通过前宣称
验收完成。旧 revision 保留，不能通过删除失败案例改善新版本结果。

## 八、明确不产生的效果

- 不因为 35 个案例形成就声称已经代表所有真实用户；
- 不把 P0 缩减为只读页面/API 文档或整理问题清单；
- 不要求第一版完成 80—120 条问题或大规模全网调研；
- 不把公开帖子数量、点赞或搜索排名直接解释为需求优先级；
- 不把公开问题中的事实陈述当作 Domeye 事件证据；
- 不保存用户名、个人资料或建立用户画像；
- 不训练、微调或认证意图模型；
- 不把只读探针、feasibility spike 或 Oracle seed 注册为生产工具；
- 不实现聊天页面、工具调用、Evidence Graph、有限假设、多源证据或 RCA；
- 不要求先实现 P2 至 P5 的全部工具，也不把当前工具枚举当成用户需求语义全集；
- 不因为 P0 通过就宣称 P1 至 P5 已实现、已部署或已在生产验证。

## 九、P1 交接效果

P0 第一版交接包至少包含：

1. 系统表面清单、Capability Discovery Ledger、能力 revision 和内容摘要；
2. 能力分层证据、unknown ledger、feasibility 结果和 Oracle seed；
3. 35 个案例、案例集 revision 和内容摘要；
4. 20 个直接问题的参考事实、能力成熟度与证据定位；
5. 5 个多轮旅程的逐轮上下文和预期状态；
6. 5 个越界问题的必须说明和禁止断言；
7. 5 个异常问题的正确状态和失败关闭规则；
8. 场景硬门禁、阻断失败和结果记录格式；
9. P1 对候选能力的 `adopt`、`defer`、`reject` 清单；
10. 开放用户目标、业务算子、目标能力与能力缺口的分层映射；
11. P1 在冻结实现级语义真值前必须形成的 Capability Catalog、Typed Tool / Operator
   Contract、算子 Oracle 和 Policy Validator 清单；
12. 后续能力增量规则和当前未覆盖项。

P1 只能读取正式交接包，不得使用未裁决草稿、人员聊天记录或模型记忆替代评测真值。

## 十、最终判定

- **通过**：P0-FE-01 至 P0-FE-06、P0-BE-01 至 P0-BE-11、P0-SCE-01 至
  P0-SCE-11 和全部硬门禁在同一 P0 revision 上具有可复核证据，P1 入口清楚；
- **有条件通过**：案例结构和边界无已知偏离，仅剩明确列出的非阻断措辞或来源补充，
  且不影响 P1 必须支持、降级和失败关闭判断；
- **不通过**：系统表面未完成勘探、能力成熟度无证据、把源码/数据/feasibility 冒充当前
  能力、数量或类别不符、关键字段缺失、事实或证据错误、上下文串扰、越界断言、异常
  误判、无效答案发布，或通过删除、降低、改写本合同要求消除偏离。

Hook 通过只能证明合同结构、阶段映射和任务边界没有发现机检偏离，不能代替系统表面
实测、Capability Discovery Ledger、feasibility/Oracle seed、35 个案例、参考事实复核、
基线执行或 P1 交接验收。

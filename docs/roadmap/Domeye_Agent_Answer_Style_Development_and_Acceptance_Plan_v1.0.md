# Domeye Agent 回答风格开发与验收计划 v1.0

> 本计划把“用户回答与内部证据分离”拆成可独立停止、修复和验收的阶段。阶段顺序是开发依赖，不是 Agent 运行时的固定流程。

---

## 1. 开发目标

本计划只解决一个问题：

> 用户看到正确、简洁、自然的回答；完整证据仍由系统内部保留和验证。

它不改变当前 RRC25 数据、Tool、Operator、Pi 滚动循环、Trust Kernel、事实边界或“拒绝和回退不算完成”的规则。

## 2. 总边界

### 2.1 必须做到

- 用户正文与内部证据记录成为两个明确边界；
- Renderer 只根据受限 Answer Context 生成用户正文；
- Response Guard 校验用户最终会看到的同一正文；
- 必要事实和限制保留，内部标识默认不展示；
- 生产验证仍能使用完整内部证据证明回答正确；
- 所有非成功状态继续失败关闭。

### 2.2 明确不做

- 不修改已冻结的首片锚点 v1.0；
- 不复用旧 Candidate 冒充新风格已经验证；
- 不只改 Prompt；
- 不只在前端隐藏原始长回答；
- 不在 Guard 之后用正则、Backend、前端或第二个模型改写答案；
- 不恢复旧 P1/P2、Question Template、固定 DAG 或 Common Plan IR；
- 不建设通用 Claim 平台、第二套证据平台或新 Workflow；
- 不在本计划中实现文档同步 Hook；该任务在回答风格稳定发布后另行进入。

### 2.3 阶段状态不能越级

| 状态 | 只表示什么 |
|---|---|
| 文档完成 | 目标和边界已设计 |
| 代码完成 | 实现存在 |
| 测试通过 | 本地和确定性合同通过 |
| Pilot 通过 | 新 Candidate 的小样本真实运行通过 |
| 正式验收通过 | 同一 Candidate 的正式证据被独立接受 |
| 生产验证通过 | 同一制品已在正式用户出口正确回答 |

任何一层都不能替代后一层。

## 3. 阶段总览

| 阶段 | 形成的独立结果 | Candidate 与真实评测 |
|---|---|---|
| A — 冻结目标效果 | 两份文档和导航成为评审对象 | Candidate 不变，不运行模型 |
| B — 实现回答边界 | 用户回答、内部记录、Renderer 与 Guard 在代码中闭合 | 尚不冻结 Candidate |
| C — 接入公开出口 | API、Backend、前端和发布验证消费同一受守卫回答 | 尚不冻结 Candidate |
| D — 冻结候选并做 Pilot | 新 Candidate 完成全量离线门和真实 3/3 | 失败即修复并重冻 |
| E — 正式独立验收 | 同一 Candidate 完成正式 30/30 和敌对场景 | 通过后才可发布 |
| F — 生产晋级与出口收口 | canary、production 和正式用户出口达到目标效果 | 同制品验证，失败关闭 |

## 4. 阶段 A — 冻结目标效果

### 目标

先把“什么是好回答”和“什么必须留在内部”写清，不急着决定所有机器字段。

### 范围

- 完成本目标效果文档；
- 完成本分阶段计划；
- 给现行架构和 Roadmap 增加导航；
- 固定成功、澄清、拒绝和失败四类用户效果；
- 固定内部标识不得进入普通正文；
- 固定拒绝、回退、停止和失败不算完成。

### 退出条件

- 目标效果不改变产品、数据与 Claim 边界；
- 不把示例变成 Question Template 或固定字符串 Oracle；
- 不要求恢复旧 Agent 架构；
- 文档状态保持 `Designed`；
- 独立评审未发现范围冲突。

### 不进入下一阶段时

文档可以继续修订，不创建运行时 Schema、Candidate 或评测任务。

## 5. 阶段 B — 实现回答边界

### 目标

在当前 Interactive Agent 内形成一个版本化的新回答边界，而不是在旧长文本外再包一层展示逻辑。

### 范围

- 定义最小用户回答结构和内部证据记录结构；
- 形成 `domeye.first-vertical-slice/v1.1`，或形成由新 Candidate 摘要绑定的版本化回答附加合同，明确新旧适用顺序，不修改旧文件；新合同只修改回答呈现、Answer Context 与 Guard，继续继承 v1.0 的固定问题、数据身份、执行链、数值 Oracle、J1–J5 和非完成语义；
- 让 Answer Context 区分“必须显示的边界”和“仅用于约束或审计的限制”；
- Renderer 生成结果优先的自然正文，不再逐字回传审计模板；
- Response Guard 同时检查事实正确、必要边界、表达长度和内部信息泄露；
- Guard `block` 后仍不得再次调用模型；
- 澄清、拒绝、失败和回退保持非成功状态；
- 保留现有 Pi、Trust Kernel、Tool、Operator、Finding 和数据身份语义。

### 必须避免

- 用删字符串或正则清理长回答；
- 让前端根据 Finding 自己重新生成最终答案；
- 用固定问句决定答案模板；
- 为回答风格新增规划器、Publisher 或第二个 LLM Reviewer。

### 定向验收

- 正常单事实和多事实回答；
- 必要范围、单位和时间不丢失；
- 内部 ID、路径、摘要和 Evidence 倾倒被 Guard 阻断；
- 过长、重复、含禁用审计栏目或内部信息的草稿被确定性规则阻断；
- 澄清只问一个必要问题；
- 拒绝和失败不被标为完成；
- 当前首片的数值 Oracle 和禁止结论完全不变。

### 退出条件

代码和测试证明：用户正文与内部记录已经在同一回答链中分开，Guard 检查的是最终正文，且没有放宽事实边界。

## 6. 阶段 C — 接入公开出口

### 目标

让用户真正只收到目标回答，同时让内部验收和发布链继续取得完整证据。

### 范围

- Sidecar 公开回答合同使用新版本；
- Backend 不重写受守卫正文，只按合同转发；
- 普通回答接口不返回完整内部证据记录；
- 生产验证器通过受信边界取得内部记录并重放正确性；
- 前端默认只展示回答、必要事实和必要边界；
- “查看依据”展示人类可理解的来源、范围和限制，不展示原始账本；
- 审计级材料进入单独的受控诊断或导出边界；
- 清点所有当前正式用户出口，确认没有旁路直接发布旧长文本。

### 定向验收

- API 中用户正文与内部记录权限边界明确；
- Backend 与前端对同一正文不做二次改写；
- 桌面和窄屏首屏能直接看到答案；
- 默认页面没有 Candidate、Receipt、SHA、路径、Evidence 清单和调用账本；
- 发布验证仍能从内部记录证明 Renderer、Guard、Finding 和 Oracle 一致；
- `/rebind`、旧 28475 或旧固定 DAG 不重新进入生产路由。

### 退出条件

从 Renderer 到用户页面只存在一个受 Guard 检查的正文；内部证据仍可被受信验证链完整重放。

### 已知出口起始清单

阶段 C 开始时必须从当前 `main` 和生产路由重新读回，不得直接沿用本表状态：

| 出口族 | 当前已知事实 | 本计划的处置边界 |
|---|---|---|
| Interactive Chat | 当前正式实现与用户入口；本专项第一轮目标 | 完成阶段 B–F |
| 报告与追问 | 已判定为旧架构文本出口 | 退出正式前端、公开 API、Backend 配置和 28474 运行时；历史源码与 release 只读保留 |
| 组合调查、回答与导出 | 已判定为旧 P2-S1 W5 本地隔离原型 | 退出正式前端与公开 API，不装配生产 runtime；历史源码与 schema 冻结保留 |
| 旧 P1 Chat 与归档路径 | 不属于正式用户出口 | 28475 停止且不可路由；历史 release 只读保留，不为本专项恢复实现 |

阶段 C 必须产出逐出口的源码存在、生产路由、用户可达性、当前状态和处置决定；缺任一项都不能宣称“所有出口已收口”。

## 7. 阶段 D — 冻结新 Candidate 并做 3/3 Pilot

### 进入条件

- 阶段 B、C 的实现和定向测试全绿；
- 首片回答后继合同已经进入权威实现基线，新 Candidate 将绑定其版本和摘要；
- 代码、Prompt、Guard、公开合同和评测协议不再继续改动；
- 旧 Candidate 继续作为旧合同的不可变历史证据，但不得作为新回答风格的实现或验收证据。

### 范围

- 从最终实现提交生成新 Candidate；
- Candidate 提交只修改 Candidate 清单；
- 运行完整离线检查、类型检查、单元测试和敌对样例；
- 用新 Candidate 做一次连续 3-run 真实 Pilot；
- 每次都核对正确事实、必要边界、表达紧凑、内部信息零泄露；
- 每次必须是直接 Renderer 成功并通过 Guard。

### 退出条件

- 3/3 首次尝试成功；
- 3/3 回答正确且达到目标风格；
- 3 条 J1 成功样本中的 fallback、拒绝、澄清、停止、Provider 失败和 Guard `block` 均为 0；
- J2–J5 的安全分支仍按原合同发生预期拒绝、block 或内部回退，但被计为成功、完成或公开 Answer 的次数为 0；
- 独立只读审查给出进入正式验收的 GO。

### 失败处理

任一 Pilot 失败都停止，不补跑、不替换 ordinal，也不把拒绝或回退算成功。修复后必须形成新的最终实现提交、新 Candidate，并从本阶段重新开始。

## 8. 阶段 E — 正式 30/30 与独立验收

### 范围

- 同一 Candidate 连续执行正式 exactly-30；
- 30 条均检查事实、范围、必要限制、自然表达和内部信息边界；
- 增加 Renderer 未见自然表达、审计式长文、重复限制、路径或摘要泄露、Evidence 倾倒和越界事实样例；这里不扩大用户问题准入，固定问题的同义问法仍按现有合同失败关闭，若要支持须另开能力切片；
- 重跑 J2–J5；
- 独立 Reviewer 重算原始证据和公开回答；
- Finalizer 只在独立证据闭合后生成最终验收记录。

### 正式硬门

- 30/30 首次尝试、无人介入；
- 30/30 正确回答；
- 30/30 直接 Renderer；
- 30/30 Guard `pass`；
- 30/30 用户正文满足目标效果；
- 内部信息泄露为 0；
- unsupported fact、范围放大和必要边界缺失为 0；
- 30 条 J1 成功样本中的 fallback、拒绝、澄清、停止和失败为 0；
- J2–J5 全部预注册安全断言通过，其中预期拒绝、block 或内部回退被计为成功、完成或公开 Answer 的次数为 0；
- 独立 Acceptance Record 为 Accepted。

30/30 是本专项进入发布的硬条件，不能只凭旧合同较低阈值、平均分、DG1 字样或旧 Candidate 绿色状态晋级。

### 失败处理

任何正式失败都停止发布。不得补跑失败 ordinal，不得用第二批结果替换第一批。代码、Prompt、Guard、合同或评测协议变化后，回到阶段 D 生成新 Candidate。

## 9. 阶段 F — 生产晋级与所有正式出口收口

### 第一轮范围（已完成）

先只晋级当前 Interactive Agent：

- 同一 Candidate 和不可变制品进入 canary；
- canary 用一次新鲜固定问题验证正确答案和目标风格；
- production 再用一次新鲜固定问题验证；
- 只有正确、简洁、直接 Renderer、Guard `pass` 且内部信息未泄露，才写生产 verified；
- 任一拒绝、回退、超时、失败或风格门失败都执行失败关闭，不恢复旧回答路由。

### 所有正式出口收口

- 清点所有仍对用户开放的 Domeye Agent 文本出口；
- 每个正式出口要么复用本合同，要么退出正式前端、公开 API、Backend 配置和活动进程；
- 归档、未路由和已退役路径不要求改造，但必须继续不可路由；
- 本轮不建设详细渠道附加合同；旧报告/追问、组合调查及旧 P1 Chat 全部按退役处置；

### 退出条件

- canary 与 production 均为正确新鲜回答；
- 默认页面和公开用户接口达到目标效果；
- 内部验证记录完整且可重放；
- 活动路由不存在旧回答旁路；
- 发布、停用和回滚身份闭合；
- 独立生产审查给出 GO。

## 10. Candidate 与评测边界

### 不改变 Candidate

- 本阶段计划和目标效果文档；
- 导航调整；
- 单纯前端布局或样式调整。

但“Candidate 不变”不表示可以在前端重写答案，也不表示无需做前端和生产验收。

### 必须形成新 Candidate

以下任一变化都影响回答语义或运行闭包：

- Answer Context；
- Renderer、Prompt 或 Draft；
- Response Guard；
- 用户回答 Schema；
- Conversation Service 或 Sidecar 用户输出；
- Candidate 绑定的相关构建产物。

旧 Candidate 和旧 30 次证据继续证明其原合同下的历史事实，但不能继承为新回答风格的实现或验收证据。

### 评测协议变化

修改 Evaluator 不一定改变 Candidate ID，但会改变评测协议身份。新增风格和泄露硬门后，旧 30 次不能直接冒充新协议验收；必须由新协议对同一新 Candidate 重新产生正式证据。

### Candidate 冻结后

任何 Candidate 内代码、模型、Prompt、Guard、数据或 Policy 变化都必须形成另一个新 Candidate。前一 Candidate 继续作为其原合同下的历史证据，但不能覆盖新代码或继续当前晋级；修复后必须从阶段 D 重新开始。

## 11. 可以后续决定的问题

以下问题不阻塞阶段 A，可以在对应阶段用最小实现和真实评测决定：

- 用户回答和内部记录的精确机器字段；
- 审计记录采用现有存储还是现有回执的受控投影；
- “查看依据”的交互位置和权限；
- 详细模式、正式报告和导出渠道的篇幅；
- 不同终端的展示上限；
- 不同详细渠道是否需要各自的附加表达量表。

紧凑模式的机器硬门与独立自然度评审量表必须在阶段 D 冻结 Candidate 前预注册。机器门只判断长度、表达块、重复、必要事实、必要边界、禁用栏目和内部信息泄露；自然度与第一遍可读性由独立人工评审判断，不能交给线上 Guard，也不能覆盖机器失败。

但以下边界不能以后再模糊决定：

- Guard 检查最终正文；
- 用户正文不暴露内部标识和原始 Evidence；
- 必要事实和范围不能丢失；
- 拒绝、澄清、回退、停止和失败不算完成；
- 不恢复旧 Agent 路由，不建设固定模板或第二套规划体系。

## 12. 下一步

阶段 A 评审通过后，开启一个只覆盖阶段 B、C 的实现任务。实现稳定并完成全部离线门后，再单独冻结 Candidate，依次执行阶段 D、E、F。

回答风格生产稳定后，再分别进入文档同步 Hook 设计和第二条能力切片。第二条切片用来验证本合同可复用，但不是本专项首片 `Released` 的退出条件；三项工作不混成一个大任务。
